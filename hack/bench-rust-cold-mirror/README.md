# Experiment: keep the packaged Docker Hub mirror out of release defaults

This is a policy experiment for review, not a recommendation to disable user
mirrors or a claim that direct Docker Hub is faster/reliable everywhere.
No PR was opened and no installed engine was reconfigured by this branch.

## Context and proposed change

The engine's generated `/etc/dagger/engine.json` contains a Docker Hub mirror
at `mirror.gcr.io`. Despite the `engine-dev` module name, the release pipeline
calls `EngineDev.Publish -> buildTargets -> Container`, so the same generated
JSON ships in release images. The mirror was added by
`fe51126b3f39470bfe251152bc4b236d8ade26ab` (#13540, June2026); its message says
only “add gcr mirror to dev engine.” Do not infer maintainer intent beyond that.

This branch removes the implicit registry entry from generated JSON while
preserving logging configuration. Integration tests already configure the
mirror explicitly through `WithEngineConfig` in `test.go`; that remains intact.
User registry configuration, credentials, CAs, ordered mirrors, fallback,
image descriptors, content verification, snapshots, egraph and GC are unchanged.
Omitting the entry (rather than emitting an empty entry) also avoids overriding
explicit legacy TOML registry configuration during JSON/TOML precedence.

The meaningful tradeoff is anonymous Docker Hub rate limiting, especially on
shared CI egress. Related history #13478 (`6e24037391`, Erik) explicitly records
rate-limit failures when nested SDK engines lacked forwarded credentials.
That is relevant context, not proof of why #13540 introduced this mirror.
Default-policy changes need rate-limit, outage, authenticated and multi-region
evidence before adoption. Explicit user mirrors must never be bypassed based
on this experiment. No adaptive racing, duplicate downloads or new snapshotter
is proposed here.

this is routing-equivalent to the default JSON generated by this branch.

Do not infer p95, macOS/remote-engine results, artifacts, fmt/clippy or dependency

## Configuration regression test

From `.dagger/modules/engine-dev`, with the desired existing dev engine selected:

```sh
dagger api with-session -- go test -count=3 \
  -run '^TestPackagedConfigLeavesRegistryPolicyExplicit$' .
```

The generated SDK requires a real session at initialization. The explicit `--`
keeps foreign Go flags out of CLI global-flag parsing. The test covers emitted
default JSON and preserved log-level settings; it does not claim rate-limit,
outage or multi-region behavior. Engine cache/registry implementation is not
modified by the patch.

Completed on this branch: the selected test passed3 repetitions in a real
session. An overlay restoring the exact old JSON policy failed all3 log-level
cases at the intended “must not impose registry policy” assertion. Logs are
under `/tmp/dagger-mirror-policy.VpS1AXFW`; initial missing-dependency,
missing-session and unseparated-command attempts are also retained. No
dependency files changed. A new engine binary/image was not built for this
config-only source patch; the runtime comparison used the equivalent config
override on the same existing binary, and the unit test checks emitted JSON.

## Rejected lead retained

An earlier host-only probe of existing containerd within-blob range concurrency
did not win:1stream4.466s vs4streams/8MiB5.047s; then4streams/32MiB4.150s vs
1stream3.767s. Parallel requests increased4→72/20 and maxRSS16→91/158MiB.
All full-blob commits verified, but a local compatibility fixture also proves
range-rejecting servers work sequentially and fail in parallel. No global
parallel-fetch setting was promoted. Comparing its direct-origin traffic to
wcprof's mirror traffic led to the controlled experiment above.
