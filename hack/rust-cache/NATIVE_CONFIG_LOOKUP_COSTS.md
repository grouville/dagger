# Repeated configuration lookup before module cache hits

One complete Go test listing opens the **same 1,649-byte `dagger.toml` 15,003 times** and performs **15,005 path stats** for it. Its contents remain unchanged. This confirms substantial repetition on the real host path; it does not establish ten seconds of file-open latency.

The earlier [API CPU profile](NATIVE_DANG_API_REQUEST_PROFILE.md) attributes **10.38 cumulative CPU-seconds** to `workspace.ParseConfigAt` under Git-client declaration lookup. That frame includes decoding, field diagnostics and SDK-scope reconciliation. It is work summed across concurrent calls, rather than ten seconds on the command's critical path. File-system waits are a separate question. The latest wcprof capture attributes 33.29 seconds of a 48.44-second main query to synchronous API intervals, which include engine processing and waits; it does not isolate TOML parsing within those intervals.

Before looking up a module-function result, `declaredGitClientsDigest` reads the configuration governing the module. For a local source, `hostFileReader` makes one request to stat the path and a second to read its bytes. `DeclaredGitClients` then calls `ParseConfigAt` and derives the relevant scope's Git-client declarations. Git and directory sources read their immutable directory instead. Repeating this preparation can therefore cost work even when the module-function result itself is cached.

The separate host trace runs the real `dagger check --module go --check test --list --all` command with a fresh source edit and CLI, normal telemetry/GC, and the selected [direct-receiver candidate](NATIVE_DANG_BUILTIN_RECEIVERS.md). `strace` follows CLI threads and filters `openat`, `newfstatat` and `statx` to the Go module's configuration path. All 4,398 ordered rows are correct and the command exits zero. The configuration's SHA-256 matches before and after. Its 58.54-second elapsed time includes tracing and is **not a latency benchmark**. Other configuration paths, parser invocations and read syscalls are not counted by this probe.

Two engine experiments now have a concrete basis:

1. **Reuse the decoded declarations for identical current bytes.** Keep reading the current file and checking which configuration is nearest. Derive declarations once for a content identity, rather than repeatedly decoding and validating the same content for every function. Reuse must preserve caller-specific warning emission, errors, scope selection and result-key contents, and keep cached data bounded and immutable. A path-only cache would fail to detect edits; reusing a derivation after reading identical bytes can preserve that behavior.
2. **Read metadata and contents in one host request.** The current lookup uses two file-service requests for an existing configuration. A combined operation could reduce transport and setup work while still reading fresh input. It needs to retain missing-file, directory, symlink and unreadable-file behavior, including compatibility with older CLIs. The trace establishes frequency, not the potential elapsed-time saving.

The simpler [one-parse experiment](NATIVE_WORKSPACE_SINGLE_TOML_PARSE.md) already removes the duplicate parse within each load. Its component benchmarks improve, but full listing is faster in only two of four pairs, so it remains disabled. The larger target is repeated preparation across calls. Neither proposed experiment above is implemented or has a measured command speedup yet.

The [archive](experiments/dang-builtin-receivers/) retains the trace, command, unchanged-content identities and exact source files for this call path. Keep complete edited-command latency as the acceptance measure; cumulative CPU savings alone do not predict seconds saved at the terminal.
