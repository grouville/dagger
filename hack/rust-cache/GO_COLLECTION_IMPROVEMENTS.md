# What improved real Go collection listing

The command remains `dagger check --module go --check test --list --all` on the real dagger/dagger checkout, returning 4,398 ordered rows. These are fresh CLI processes and real edits on a warm development engine. Telemetry, ordinary GC, successful session cleanup and final log flushing are included. This is an experimental engine, CLI and Go module together, not stock released Dagger.

The newest [sealed-metadata encoding screen](NATIVE_SEALED_METADATA_JSON.md) is **not another selected improvement**. Complete test-edited listing moves **8.75 → 8.49 s**, ordinary-source listing **5.44 → 5.35 s**, with mixed paired results. It reduces measured lock contention without establishing enough command-level benefit for its added cache. Eighteen Go commands, 28 Rust/native-cache cases and race checks pass; all 800 getters remain. The unchanged pipeline remains the acceptance criterion.

The progression from roughly 40 seconds toward 12 seconds comes from engine/CLI changes, Go module changes and the embedded Dang interpreter. Each row below is its own controlled comparison; different source revisions, engine builds and cache states prevent treating the rows as a single additive waterfall.

| Improvement | Where | Complete-command comparison |

| Read typed listing metadata in bulk and project immutable fields without per-field cache work | Engine + CLI | **40.86 → 26.76 s**, ordinary-source edits |

Evidence and scope: [typed metadata](NATIVE_TYPED_ARTIFACT_METADATA.md), [initial batched facts](NATIVE_GO_BATCHED_DISCOVERY_FACTS.md), [getter identity and snapshots](NATIVE_COLLECTION_GETTER_CONTENT.md), [batched package discovery](NATIVE_GO_BATCH_PACKAGE_DISCOVERY.md), [method classification](NATIVE_DANG_COERCED_METHOD_HOISTING.md), [error context](NATIVE_DANG_LAZY_ERROR_CONTEXT.md).

The [snapshot-directory follow-up](NATIVE_GO_TEST_DIRECTORY_DISCOVERY.md) removes 800 existence queries with one snapshot walk. All four test-edit pairs improve, with lower CPU and allocation in each. It leaves 804 module evaluations and uses linear membership in a 103-directory list. All 24 timing commands return correct rows and exit successfully; seven focused commands pass. This is a module-only follow-up on the experimental API, without an engine change or measured cold-start benefit.

The earlier **19.70 → 9.30 s** result belongs to the [first native-input prototype](NATIVE_GO_NATIVE_TEST_DISCOVERY.md), after an ordinary-source edit with unchanged test files. Test-file edits did not show that improvement. Later revisions refine this mechanism. It is not evidence of a ten-second cold start or a ten-second test-edit command.

The earlier roughly 100-to-40-second period was also not engine-only. Parallel Go discovery and retaining module ownership contributed alongside engine/runtime and host-file-walk improvements. The [historical report](NATIVE_GO_FULL_LISTING.md) preserves those comparisons and their limits.

## What is ready

The two final Dang fixes each reproduce independently on pristine upstream and pass its full interpreter race suite. Their minimal patches and review descriptions are prepared. No new PR is opened.

The combined listing prototype also passes real discovery, module-boundary and collection test-execution checks. The engine getter-identity change has focused cache/resource race coverage, and bulk metadata/projection has DagQL race and output-equivalence coverage. This does not establish universal compatibility across SDKs. The Go snapshot variant changes the direct discovery API; compatibility and a standalone upstream port remain work. The bulk metadata API requires the corresponding CLI and engine changes.

The latest shared-function-metadata experiment is not counted as another speedup: test-edited listing is **11.74 → 11.69 s**, faster in two of four pairs; ordinary-source listing is **5.96 → 6.25 s**, faster in one pair. It stays unselected. Its source-only protocol completes the test-layout transition in both arms before measured pairs, correcting an earlier first-pair confound. All 24 commands return correct rows and exit successfully.

A subsequent [cold-cache study](NATIVE_GO_COLD_LISTING.md) measures three independent new engines: **20.19 s median from engine start through first listing**, followed by **5.85 s** for ordinary-source edits and **12.27 s** for test additions. The image is already local and the host OS page cache is not flushed. All 12 commands succeed with correct rows. This is first use with an empty Dagger cache; a retained-cache restart is not measured.

Three seconds and integration of these collection changes into the Rust module remain unfinished.

The [telemetry recovery-reader follow-up](NATIVE_TELEMETRY_RECOVERY_READER.md) preserves the full workflow and saves about 452 MB after a test edit, but is not counted as a speedup: complete listing changes **8.45 → 8.68 s**, faster in only one of four pairs. Its one-line fix and benchmark are pushed separately for review; the diagnostic switch stays off. All 24 timing commands, 18 Go checks and 28 Rust/native-cache cases have their expected outcomes. Both lossless test-edited profiles still execute all 800 getters. This is an allocation result whose latency tradeoff remains unresolved.

Two [callback argument screens](NATIVE_DANG_CALLBACK_DISPATCH.md) also remain unselected. The provenance map is already allocated on the stack, so omitting it saves no heap allocation. Concrete native callback dispatch removes 336 bytes and two allocations per component call, and about 311 MB from test-edited listing, but elapsed time changes **8.22 → 8.81 s**, faster in only one of four pairs. Ordinary-source listing is **5.47 → 5.37 s**. All normal getters, test-discovery hits, Go/Rust execution checks and race suites remain correct. These are allocation findings, not another demonstrated listing speedup; the source is retained without a new PR proposal.

Two further [discovery experiments](NATIVE_GO_DISCOVERY_PATH_WALKS.md) preserve normal getters and the complete pipeline. Batched module-header reads remove 79 SDK requests but leave test-edited listing effectively flat at **9.36 → 9.28 s**; that complexity is not selected. A single ownership walk improves ordinary-source listing **6.30 → 5.73 s**, faster in all four pairs. Its test-edit cohort is inconclusive under varying host CPU pressure despite **17.13 → 16.11 s** medians, so it remains experimental. Fourteen focused ownership checks and a check against unchanged production code pass. All 48 timing commands across the two experiments have correct rows and successful exits. These are warm-engine observations, with telemetry and cleanup included.

The [interface-matching algorithm candidate](NATIVE_INTERFACE_CANDIDATE_INDEX.md) is now measured on a fifth isolated engine. Complete test-edited listing improves **8.56 → 8.27 s**, faster in all four pairs, with about **408 MB less allocation**. Ordinary-source listing is essentially flat at **5.46 → 5.40 s**. All 800 getters still execute, with 799 unchanged test-discovery hits. Eighteen Go checks, 28 Rust/native-cache cases and the port's DagQL/SDK race suites pass. Standalone sparse schema construction improves **51.99 → 8.74 ms**, but that larger component gain is not the command-level gain. Tiny schemas cost an additional 1.92 µs and two allocations. Exact inputs rebuild to the measured engine's identical binary. The standalone source is pushed to the fork; no PR is open. Current cold and Rust latency effects remain unmeasured.

The subsequent [native stored-item prototype](NATIVE_COLLECTION_STORED_ITEMS.md) establishes a larger structural gain: **10.81 → 7.04 s** after test edits, faster in all four pairs, with **804 → 4** module evaluations. It remains experimental because ordinary-source listing regresses **6.00 → 6.52 s**, and the new stored-getter form needs broader validation. SDK requests are essentially unchanged; the gain removes module setup. All 24 timing commands have correct rows and successful exits. Cold performance is unmeasured for this prototype.

A follow-up keeps the existing Go getter unchanged and shares decoded receiver JSON while constructing fresh invocation objects. The component improves **0.507 → 0.351 s** for 800 getters, but complete test-edited listing is only **10.91 → 10.61 s** (three of four pairs faster), with ordinary-source listing **6.06 → 6.18 s** (one pair faster). It remains disabled: the small, mixed complete-command result does not justify selecting a new process cache. Both lossless wcprof captures retain 804 evaluations and 1,494 SDK requests; all 24 timing commands are correct, the SDK race suite passes and six real module checks pass. This is evidence about preparation cost, not a completed getter-batching implementation or a cold result. [Full evidence and source](experiments/shared-receiver-decode/).

The [schema-reuse retest](NATIVE_DANG_PREPARED_SCHEMA.md) is stronger: test-edited listing improves in all four pairs, CPU falls 62.39 → 56.63 CPU-s and allocation 15.33 → 13.63 GB. The unchanged module still executes all 800 getters; schema opens fall 804 → 2. Six Go checks, eighteen actual module-source edit probes and 28 Rust/native-cache cases pass with their expected outcomes. The flag is restored to disabled; this remains a development-stack candidate dependent on the compiled-declaration prototype. Cold and Rust performance effects are unmeasured, and no new PR is opened.

An [indexed module-ownership screen](NATIVE_GO_MODULE_OWNER_INDEX.md) keeps the normal getter but replaces repeated all-module searches with path-ancestor lookups. It remains unselected: test-edited listing changes **10.73 → 10.59 s** in three of four pairs; ordinary-source listing stays **6.37 → 6.37 s**. All 24 timing commands and eight focused checks pass. Profiles retain 800 getter executions and about 81 MB of receiver JSON, exposing the limit of optimizing lookup while still reconstructing every owner for every package. Prepared-schema reuse is common to both arms; these numbers are not another additive gain.

The follow-up [indexed owner-facts candidate](NATIVE_GO_INDEXED_OWNER_FACTS.md) also removes full-owner reconstruction from the collection receiver. Test-edited listing improves **11.47 → 9.56 s**, ordinary-source listing **6.54 → 6.21 s**, faster in all eight pairs. Getter receiver data falls 81.4 → 52.1 MB and converted lists 392,000 → 6,400, with all 800 getters and existing test-discovery hits retained. Nine checks pass, including custom settings through real tests, binary execution and generation; a deliberate settings-loss mutation fails the new check. The implementation is pushed to the Go fork and its review description is prepared. This remains a candidate on the development stack, without a new PR or current cold/Rust performance claim.

The [callback-caller retest](NATIVE_DANG_CALLBACK_CALLER.md) provides another useful candidate: **10.01 → 9.53 s** after test edits and **6.75 → 6.13 s** after ordinary-source edits, faster in all eight pairs. It removes roughly 1.1 GB of allocation while retaining callback execution, fresh invocation state and normal getter/discovery behavior. Its standalone patch and full race suite pass on pristine interpreter source; development interpreter/SDK race suites and 37 Go/Rust pipeline cases also pass. An unsafe unconditional-sharing variant fails the custom-callable regression. The separate [parallel-admission retest](NATIVE_GO_LISTING_LOCKS.md) stays disabled after mixed complete-command results. Key-list conversion costs only 0.16 sampled CPU-s in the motivating capture, so no new primitive conversion cache is added.

[Three subsequent setup screens](NATIVE_GO_DISCOVERY_SETUP_SCREENS.md) remain unselected: compact owners save allocation without a convincing latency gain, global marker batching removes searches without improving test-edited listing, and parallel test-file reads regress that workload. All 72 timing commands return correct rows and exit successfully. The independent [nested-list element type fix](NATIVE_DANG_NESTED_SELECTION_ELEMENTS.md) reproduces on pristine upstream and passes its race suite; it is a correctness fix, not another measured speedup.
