The [validated literal-include walk](NATIVE_FILESYNC_LITERAL_WALKS.md) reduces visited entries to 237,287 and improves complete listing **55.81 → 52.03 seconds** in a separate balanced cohort. The original diagnostic below identified that opportunity.

The next filesystem target is parent-directory synchronization. A complete diagnostic visits **5,581,952 host entries** across **2,426 directory-walk streams**. Of these, **1,213 parent-only streams visit 5,351,714 entries (95.9%)**; the 1,213 content streams visit 230,238. This establishes repeated traversal work, not a measured speedup.

The diagnostic CLI delegates every original FS operation and counts callbacks before the include/exclude filter. Listing completes in 53.60 seconds, exits successfully and returns the same 4,398 rows. Telemetry and ordinary GC remain enabled; CPU profiling and wcprof are disabled for this capture. Instrumentation timing is not a clean performance comparison.

`engine/filesync/filesyncer.go:syncParentDirs` creates a remote filesystem rooted at `/` (or the Windows drive root), includes the absolute client directory relative to that root, and excludes its immediate children. It then feeds this directory walk into the existing local mirror. This produces the metadata of the selected directory and its ancestors. The host walker still enumerates siblings at each level before its filters discard them. Every content snapshot repeats this preparation.

For example, one parent request for `core/integration/testdata/modules/go/ifaces/test/dep` visits 5,045 entries and 1,345 directories. Its include is the literal absolute-relative directory; its exclude is that directory plus `/*`. The target's ancestry contains only a handful of directories. The count includes visited siblings, not files transferred into the snapshot.

The populated `/tmp` on this development host amplifies the cost. Results must therefore include controlled ancestor widths as well as real-repository commands; a gain measured here must not be generalized to a clean host. The algorithmic problem remains: work depends on unrelated siblings instead of the selected path's depth.

A possible generic fix is to let the native filesystem walk a single literal include by accessing its ancestors directly, then walking its selected subtree, while retaining the existing filter. Another option is an explicit parent-stat operation in the internal filesync protocol. Neither is implemented or selected yet. The first avoids an engine restart but needs careful parity checks; the second states the intent directly but adds protocol and compatibility work.

Before selecting either approach, compare complete emitted stats and order against the current implementation, including permissions, symlink ancestors and targets, missing paths, cancellation, filter callbacks and metadata normalization. The existing parent synchronization maintains the mirror's metadata: skipping it is not a correctness argument. Keep hashing, ownership and xattr normalization behavior intact. Then measure sibling-width scaling and balanced full commands on the same engine.
