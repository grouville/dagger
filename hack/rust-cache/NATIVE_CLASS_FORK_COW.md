Client forks can share immutable class-definition storage and copy it only when a branch changes a field or interface. This reduces allocation consistently in complete Go test-edited listing, but establishes only a modest, variable latency result. The prototype is retained for review; three seconds and a stock-engine performance result remain unfinished.

Class.ForkObjectType currently copies every field map, declaration-order slice and interface map, even when the fork only reads them. The candidate gives each fork a private state record, lock, owner and view, while sharing read-only definition storage. A writer detaches its maps and order under its own write lock before modifying them. The source marks storage shared while holding its read lock, so no writer can mutate storage retained by a concurrent fork. Repeated declarations of the same interface preserve existing registration and invalidation while avoiding an unnecessary map write. Value copies of one class continue to share their branch's state. No live execution client or receiver object is shared.

This changes fork preparation from copying all fields to allocating one fixed-size record per type, with field copying paid on mutation. Complete schema emission still traverses the fields, so the whole pipeline has not acquired constant-time schema construction. The production diff is 55 insertions and 27 deletions in dagql/objects.go, plus focused tests. The tradeoff is a shared-storage flag, an extra state indirection and an ownership invariant that future mutators must maintain. Existing lock ordering and cache invalidation remain. Native Rust compiler artifacts and incremental state continue to use the existing Dagger filesystem snapshots.

The sharing audit also found an independent [field-history isolation bug](PR_CLASS_FORK_HISTORY_ISOLATION.md). Both experiment modes include its two-line fix. The correctness commit and COW commit are separate, and the COW review branch is based on the fix. No performance claim is made for that fix itself.
