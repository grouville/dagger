# Index structural interface candidates

Indexing structural interface candidates improves complete Go test listing after a test edit **8.56 → 8.27 seconds median**, faster in all four balanced pairs. Engine allocation falls **9.99 → 9.58 GB** and CPU **41.88 → 40.49 CPU-s**. Ordinary-source listing is essentially flat at **5.46 → 5.40 seconds**. This is the same experimental stack and warm isolated engine in both arms, with a fresh CLI, telemetry, ordinary GC, output, cleanup and final flushing included. No PR is open.

The command is `dagger check --module go --check test --list --all` on real dagger/dagger. Every measured command returns the same 4,398 ordered rows and exits successfully. Each workload has four alternating pairs after both modes complete test-addition/removal initialization; all 24 commands are retained. The median paired test-edit saving is 0.46 seconds; the difference between the column medians above is 0.29 seconds. These are different summaries of the same cohort. Neither should be added to earlier studies' gains.

The matching change preserves the existing pipeline. Lossless profiles in both modes retain **804 module evaluations, 1,494 SDK requests, all 800 getter executions and 799 unchanged test-discovery hits** after a test edit. Source-only profiles retain three evaluations, 572 SDK requests and all 800 getter/discovery hits. All four captures have zero dropped or open events. Eighteen Go checks cover discovery, ownership, custom settings, source snapshots, rebinding, selected tests, binary execution and generation. Twenty-eight Rust cases cover changed/restored test names, selected passing/failing tests, invalid neighboring crates, repair and public workspace APIs with native caching enabled. Four native-cache statistics calls each report two actions and two hits. A separate warmed-invalid-source check confirms the same compiler diagnostic and failure status in both modes. These establish behavior and compiled-result reuse, not a Rust edited-build speedup.

The indexed engine is a fifth isolated engine with its own retained cache volume; the four previous engines and volumes are unchanged. The exact port passes the full DagQL race suite in **111.267 seconds** and the Dang SDK race suite in **4.523 seconds**, with the candidate enabled. Rebuilding produces a byte-identical executable, SHA-256 `0df377c84e39ae7f85914fa1eb6b8eeb425c7e50454cb55db8e4742db5c8e856`. Sources and diagnostic switches are restored, with no active client or open client database. First-use and retained-cache restart performance remain unmeasured for this change.

The engine currently starts with every object/interface pair and repeatedly removes invalid relationships. The candidate builds a temporary index of visible field names and starts each interface from types exposing its least common required field. The original type, argument and recursive compatibility rules still decide which relationships survive. Explicit declarations remain facts, including declarations without matching fields. Empty interfaces still consider every eligible type.

Required-field lists are reused only within one reconciliation pass. Objects with many fields use individual lookups for the few required names; sparse objects use one field scan. A private field-count method reads the existing class map under its existing lock, then releases it before any lookup. Fully declared objects need no index construction, and a single interface retains direct candidate seeding. There is no global cache, new lock, public API or persistence-format change.

The tiny fixture costs an additional **1.92 µs, 336 bytes and two allocations**. The one-interface declared fixture is effectively flat. This constant overhead and the added indexing logic are explicit tradeoffs; the complete-command cohort above establishes a modest gain on test edits rather than the component fixture's several-fold gain.

Four fresh-process pairs per shape use Go 1.26.6, GOMAXPROCS=8 and 150 ms per benchmark. Every iteration constructs a fresh schema, with construction included in the timer; compiled code is warm. Order alternates between pairs, pressure observations are recorded, and every attempt is retained. This is neither first-use CLI timing nor an empty-cache engine measurement.

The final full DagQL race suite passes in **66.065 seconds**. Focused regressions cover recursive relationships and their removal, explicit declarations as evidence, empty interfaces, sparse candidate work and avoiding full field-table copies. Existing tests cover views, variance, installation order and concurrent registration. The sparse probe records **4,160 compatibility `FieldSpec` calls on unchanged code and 64 with the candidate**, with all intended matches preserved. Index construction still reads field metadata, which is included in the benchmarks. Its compatibility-call bound fails on unchanged code. The declared, empty-interface and recursive cases also pass unchanged code. The baseline reconciliation body exactly matches the function sampled in the retained engine's CPU profile, so this targets an active path.

The first index regressed dense and already-declared shapes. Per-pass field-list reuse and direct seeding for one interface address those costs. A later control exposed a more relevant regression: scanning every field changes the 512-object core-shaped fixture **18.87 → 25.38 ms** and nearly doubles allocation. Adaptive name lookups fix that measured regression. All intermediate sources, failed fixture compilation, race runs and benchmark cohorts remain in the evidence; their results are not pooled with the final cohort.

The follow-up Go ownership confirmation remains unselected: its 12 complete commands all return correct rows and exit successfully, but medians are **15.12 → 19.74 seconds** under variable CPU pressure, despite three of four paired differences favoring the candidate. Quiet admission does not guarantee quiet execution. This is additional evidence against claiming a stable test-edit gain from that separate module change.

Spill-file recovery borrows a pooled telemetry reader without returning it; the [reader-return experiment](NATIVE_TELEMETRY_RECOVERY_READER.md) saves about 452 MB but remains unselected because test-edited listing changes 8.45 → 8.68 seconds, faster in only one of four pairs. A later [argument-preparation screen](NATIVE_DANG_CALLBACK_DISPATCH.md) shows that the positional-provenance map is already on the stack; its sampled caller-frame allocation was insufficient evidence to blame that map. Concrete native callback dispatch does save allocation but also fails the command-level latency gate. Telemetry delivery and the command's completion barrier remain required. Sampled allocation deltas can lag natural GC and are attribution evidence rather than exact allocation accounting.
