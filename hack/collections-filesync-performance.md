# Read parent metadata without scanning unrelated directories

The new filesync operation removes a width-dependent scan before local directory
imports. It helps any module that imports local files, without caching host state
or changing content-based invalidation. The 500 ms goal remains unmet for expanded
artifact/check discovery. The measured gain depends strongly on ancestor width:
the follow-up under a narrower path shows essentially unchanged CLI latency.

## Ordinary commands and edits

The confirmation uses five observations per variant, in ABBA blocks, on the same
retained Dagger volume. Timings include complete CLI exit. Both variants use the
same experimental SDK/Dang stack; these absolute times are not the performance
of an ordinary branch build. Cloud export is disabled.

| Command or real edit | Baseline median | Parent metadata operation |
| --- | ---: | ---: |
| `dagger list -a`, greetings-api | 1.473 s | 1.413 s |
| `dagger check -l --all`, greetings-api | 1.468 s | 1.373 s |
| New Dang source comment, then standard native `dagger check` | 310 ms | 269 ms |
| New input bytes, then native `dagger generate` | 388 ms | 366 ms |

The [confirmation](collections-qa-performance-data/ancestor-request-confirmation/report.md)
has 54 correct commands: 40 ordinary observations, 12 explicit
primers and two mixed-version compatibility checks. New client/old engine and
old client/new engine both return the expected listing. The independent initial
[72-command matrix](collections-qa-performance-data/ancestor-request-runtime/report.md)
also covers `ws ls`, generator listing, core/module calls, actual export writes,
generated bytes, deliberate failing checks and a selected real greetings Go
test. Its smaller two-observation timings are retained separately; some controls
move worse, so it does not establish universal latency improvement. Neither
matrix measures SDK code generation or service startup.

## Work removed

Before synchronizing a requested subtree, the engine synchronizes its ancestors.
The old request starts at the filesystem root and uses include/exclude filters
to retain the known ancestor chain. It still reads and sorts unrelated siblings
at each level. This cost grows with the width of directories outside the project.

The engine now requests directory-only parent metadata explicitly. The client
validates the request, checks the complete chain and reads fresh metadata for
its directories. It never opens file contents or enumerates siblings. The actual
subtree synchronization, content digests, cache scopes and invalidation remain
unchanged. The old filters are still transmitted for older clients; unsupported
or nonliteral targets retain the existing path.

The number of filesystem operations depends on path depth rather than sibling
count. Path construction and repeated native lookup still process path prefixes;
this is not a claim that all byte-level processing is strictly linear in depth.
With 1,000 siblings at each of four synthetic levels, the measured traversal
falls from 4.92 ms to 15 microseconds. With no siblings, it improves from 35 to
15 microseconds. These are microbenchmarks, not whole-command times.

A fixed `filesync.syncParentDirs` wcprof marker is compiled into both measured
engines. Separate captures show ten parent operations occupying 94.4 versus
7.3 ms of interval union; concurrent intervals are counted once. Their enclosing
host-directory operations occupy 123.4 versus 48.1 ms. These nested durations
cannot be added or subtracted directly from CLI latency. Those captures followed
restart and selected-check warmup rather than an identical full-listing primer.

A separate [fully primed profile pair](collections-qa-performance-data/ancestor-request-warm-profiles/report.md)
now runs the identical full-listing command immediately before each capture.
Parent synchronization occupies 114.7 versus 10.5 ms of interval union, while
the enclosing host-directory union falls from 140.7 to 36.7 ms. All four
primer/profile commands return the exact listing. Profiled CLI times remain
excluded from the ordinary medians above.

This test machine has roughly 6,000 `/tmp` entries, partly accumulated by the
investigation. That amplifies the old scan's cost. The controlled width benchmark
establishes the algorithmic improvement, but the measured command saving is not
a promise for every user's filesystem.

The [lower-width follow-up](collections-qa-performance-data/ancestor-request-low-width/report.md)
copies the identical public fixture and lock bytes beneath the repository's
ignored `bin` directory, with its own Git boundary. It avoids the wide `/tmp`
ancestor. Three ordinary samples per variant give **1.447 → 1.443 s**: effectively
flat. Separate, fully primed profiles reduce parent-sync interval union only
**10.82 → 6.69 ms**. All 12 commands return the exact 14 rows; the owned copy is
removed and the original fixture and engine are restored. The fixed variant
order and small sample count do not establish stable percentiles. This result
qualifies the larger earlier gain rather than supporting another general
whole-command speedup claim.

## First call on a fresh Dagger volume

The [cold follow-up](collections-qa-performance-data/ancestor-request-cold/evidence/report.md)
uses two new engine volumes, with one full listing and an immediate repeat on
each. All four commands return the expected 14 rows.

| Command boundary | Baseline | Parent metadata operation |
| --- | ---: | ---: |
| First listing on a new Dagger volume | 24.938 s | 24.568 s |
| Immediate repeat | 1.623 s | 1.516 s |

This single, baseline-first pair does not establish a cold-start improvement.
Engine CPU is nearly identical: 87.82 versus 87.97 CPU-seconds. Engine image,
SDK blobs and host page caches remain available; provisioning/startup is excluded
from the CLI timer. The parent operation does not remove the bulk of cold work.

Disk counters also explain why the repeat needs care: the baseline records
535 MiB of writes during its warm command while dirty host pages decline, whereas
the candidate records most writes before its cold command exits. These boundaries
are consistent with deferred writeback, not proof of new work caused by the warm
listing. No multi-second disk-pressure stall occurred in this pair. Both temporary
engines and volumes were removed, and the source fixture was unchanged.

## Compatibility and upstream scope

The source change is independent of the experimental SDK stack. It contains an
additive filesync option, strict request validation, a directory-only filesystem
view, the engine opt-in and focused tests. It does not introduce a cache, TTL,
background daemon or change to the public command UX.

Point lookup uses native filesystem case and path-access rules, unlike directory
enumeration. The unchanged outer filter can suppress late missing-path errors;
this is still a filesystem race, not an atomic snapshot guarantee. Directory-only
packets and rejection of conflicting request modes are tested through actual
in-memory `DiffCopy` dispatch.

The measured Linux binaries contain the first explicit-request implementation.
The applied production source additionally accepts the protocol's `/` walk root
on Windows; this predicate already accepted `/` on Linux, so Linux behavior is
unchanged. Nine focused normal and race groups pass, and the fsutil test package
cross-compiles for Windows. Cross-compilation does not establish Windows runtime
parity. The portable freshness test compares normalized metadata and changed
mtime rather than assuming Unix permission bits. Its final test-only correction
passes all nine groups with ordinary checkout dependencies. The
[portability evidence](collections-qa-performance-data/ancestor-request-portability/ancestor-request-v2/report.md)
preserves the exact relation to the measured Linux binaries.

The [source evidence](collections-qa-performance-data/ancestor-request-source/report.md)
preserves the measured implementation, build hashes and algorithm tests. The
[broader performance review](collections-bootstrap-performance.md#follow-up-eliminate-work-before-adding-concurrency)
keeps this change separate from held metadata/telemetry experiments. Cold-volume
performance must be reported separately from these warm and edit measurements.

The source and tests are committed as `0d1c32e29f`. The
[remaining-path audit](collections-qa-performance-data/ancestor-request-next-audit/report.md)
identifies three avoidable nested module calls in the existing Go-module helper
patch. It also explains why Git lock pins alone do not authorize skipping the
current session's remote visibility check.
