# Remove local connection overhead before adding a daemon

The small normal-path improvement is committed as `e6e723145e`: the existing
Docker inspection now supplies the exact state, avoiding a redundant `docker start`
only for `running`. The [32-command comparison](collections-qa-performance-data/managed-engine-start-runtime/report.md)
finds lower paired process-tree CPU and native generation at 293 → 280 ms; core
wall medians are flat at 244 ms. Unknown states and other backends keep their
previous behavior, and stopped-engine resumption passes. This is independent of
the Unix connection prototype below and does not require socket provisioning.

The follow-up keeps the normal Docker driver and changes only its connection
mechanism. It confirms a 77–122 ms median reduction across four warm and two
fresh-edit flows, including writing new generated bytes. This remains an isolated
prototype, not automatic socket provisioning in the branch.

The [raw numeric pairs and restoration evidence](collections-qa-performance-data/container-unix-runtime/report.md)
contain three alternating pairs per case. All 50 commands pass, including
exact-flow primers and check failure/restoration sentinels. New file visibility
is sampled every 5 ms; complete CLI exit is timed independently. Each edit uses
previously unseen bytes. The check fixture is a native Dang module and generation
is an authored generator, not Go/TypeScript SDK code generation. Cloud is disabled
and the engine volume is retained. Do not subtract values between this round and
the earlier direct-driver round to estimate a Docker-probe cost.

Both arms use one identical CLI, the normal `container+docker` driver, its Docker
availability probe and image loader, independent HTTP pools, and the initial
connection plus three proactive warm connections. Only an explicit private-socket
query selects the new dial path. The [source proof and focused tests](collections-qa-performance-data/container-unix-source/report.md)
also catch and correct a prefetch cancellation race: background Unix dials must
retain the cancellation-independent lifetime of the original stdio subprocesses.
The initial Unix dial remains cancelable. Normal and race tests pass; two negative
witnesses fail against the corresponding uncorrected sources.

## What changes in the experiment

Both selectors use the same unmodified CLI, the same engine process, fresh
sessions, identical source paths and the same retained Dagger volume. Both
retain the Docker image-store attachable. The temporary socket sits in a host
user-owned directory with mode 0700; its mode is 0660 with the intended group.
The original engine remains stopped and untouched. Cleanup removes only the new
container and socket directory, preserving the retained volume and fixture bytes.

The direct driver uses `net.Dialer` instead of `docker exec … buildctl dial-stdio`.
It also skips the container driver's `docker version` availability probe.
Therefore the result includes both driver admission and connection costs; it
must not all be attributed to runc or tunnel setup. No daemon, background work
after exit or workspace-result cache is introduced.

The [upstream design audit](collections-qa-performance-data/local-unix-design/review.md)
recommends preserving the image/container driver and replacing only a validated
connector path. Automatic provisioning still needs reliable local-backend
detection, binding of the socket to the intended daemon/container, permission
and lifecycle handling, and fallback for unsupported or older engines. A Unix
Docker endpoint alone does not prove the daemon shares the host filesystem.
Bypassing Docker exec also changes where access is checked; session tokens are
not global engine authentication. Remote Docker and Desktop support have not
been demonstrated by this Linux experiment.

The [managed-driver follow-up](collections-qa-performance-data/container-unix-production-design/review.md)
identifies a way to avoid another per-command inspection: the normal image driver
already inspects its selected container. That response could return the immutable
container ID and managed endpoint descriptor together. Creation already receives a
container ID from `docker run`. These existing boundaries are preferable to a global
socket cache keyed by a mutable container name. This design is not implemented;
the controlled `container+docker` benchmarks also exclude the normal image driver's
inspect/start path.

## Remaining listing work

Additional wcprof instrumentation separates Git connection acquisition, request
latency and local reference processing. The source-context and SDK stages are
also marked without changing their execution order. Focused normal and race
tests pass, and the two full-listing captures have no dropped or open operations.
The [catalog and diagnostic source evidence](collections-qa-performance-data/catalog-http-diagnostic/report.md)
keeps these observations separate from the ordinary command measurements.

The [two fully primed wcprof captures](collections-qa-performance-data/catalog-http-diagnostic/git-http/profile-evidence/report.md)
show seven Git probes using already-open connections: no DNS, TCP connection or
TLS setup. Request-write to first-byte intervals occupy approximately 385 ms of
the wall clock, while local reference validation and sorting total less than
0.5 ms. This is network/server response waiting, not a measurement of server CPU.
Changing the local reference data structure cannot remove that cost. The probes
already share results within the session; a persistent visibility cache would
change the access and freshness boundary.

A [bounded protocol comparison](collections-qa-performance-data/git-advertisement-v2-v2/report.md)
subsequently tests the response-size hypothesis. Across ten target-specific timed
pairs, v2 transfers 1,910 bytes versus 54,270 for v0, but response waits do not improve
consistently. Parsing remains below 0.6 ms. It uses one host HTTP/1.1 connection,
not an engine or HTTP/2 comparison. Keep the engine protocol unchanged on this
evidence. The archive retains an earlier two-primer harness failure separately;
the corrected 22 requests all validate, for 24 total requests and no Cloud export.

The longest SDK load includes a 94–96 ms registration process, preceded by only
6–8 ms of source-context loading. Overlapping those two stages offers a small
upper bound here. Eliminating registration work through the static SDK entrypoint
is more promising. These intervals overlap other work and must not be added as
predicted command savings.

The remaining registration processes are an SDK opportunity already covered by
the static entrypoint direction. They should not be replaced by a second metadata
format or a global cache of module objects. The previously tested shared HTTP/2
transport remains isolated: even after correcting cleanup scheduling, it slows
warm generation. The [broader investigation](collections-bootstrap-performance.md#follow-up-eliminate-work-before-adding-concurrency)
retains those negative results alongside the improvements.

The [collection follow-up](collections-qa-performance-data/collection-expansion-followup/report.md)
tracks a separate module-owned improvement, now pushed as
[`grouville/go:perf/discovery-path-normalization`](https://github.com/grouville/go/commit/93d0f1b5288ccaa47aa4d5befd809a25f6ffb801).
It replaces repeated public module calls for pure path normalization with a private
helper. The exact source passed the discovery/lookup checks and improved an earlier
eight-pair warm series by 84 ms. That timing is historical, not an additional saving
measured on the connector stack above; the active greetings fixture is unchanged.

Two authored Go invocations expose another generic target: each spends 58–67 ms
between the runc monitor starting and the first nested dispatch query. The profiler's
`exec.processRun` label includes that startup interval; it does not isolate user code.
Their nested schema-building work totals approximately 0.5 ms each. Further profiling
must split container/shim/language startup from nested-client admission before choosing
a fix. Eliminating the authored calls or adding a broad schema cache does not follow
from those observations.

## Scheduling experiment: earlier work did not mean earlier completion

A bounded module-loading pipeline starts a ninth source resolution before the first
eight registrations finish. Its focused tests pass, but the complete CLI comparison
does not improve:

| Flow | Existing scheduling | Separate source/module limits |
| --- | ---: | ---: |
| Warm `check -l --all`, five observations per arm | 1.382 s | 1.389 s |
| Warm `list -a`, three observations per arm | 1.396 s | 1.407 s |
| First-seen app comment → `check -l --all`, three observations per arm | 1.426 s | 1.436 s |

The [42-command experiment](collections-qa-performance-data/module-load-pipeline-runtime/report.md)
uses four independently primed ABBA engine blocks, with identical CLI, SDK contents,
fixture paths and retained volume. All correctness checks pass; Cloud is disabled.
These are pooled block observations, not independently randomized engine pairs.
Separate wcprof captures confirm that the ninth source starts about 147 ms earlier,
but catalog duration falls only 24 ms in that instrumented pair. The same seven Git
advertisements and six runtime processes remain. Overlapping work outside the
critical path does not establish a command saving. Keep this prototype out of the
production change set unless another measured workload justifies it.

The next structural experiment splits the small PID1 reaper from the dependency-heavy
attachables program. The existing binary initializes those dependencies in both
processes, before either reaches its selected entrypoint. A separate light PID1 can
avoid one initialization while preserving the helper process, FD3 readiness protocol,
signal forwarding and child reaping. Its extra bind mount and packaging cost belong
in the full comparison. Focused normal/race tests and the actual PID1 namespace
test pass. Twelve alternating host-process pairs with an unmatched entrypoint
measure startup/exit at 10.019 → 1.471 ms, without running PID1 or attachables
behavior. Separate initialization traces report 505 → 19 package-init records
and 3.402 MB → 1,728 bytes of initialization allocations. Instrumented timings
are excluded from the ordinary sample set. Neither this microbenchmark nor the
58–67 ms pre-query interval predicts the complete-command saving.

The whole-command result is narrower than the startup microbenchmark. The first
[36-call trial](collections-qa-performance-data/split-init-runtime/report.md)
improves warm check listing 1.423 → 1.346 s but has mixed artifact/edit results.
A [40-call confirmation](collections-qa-performance-data/split-init-confirmation/report.md)
puts artifact listing at 1.409 → 1.407 s (flat) and distinct-comment listing at
1.459 → 1.423 s. Fresh native generation improves in both trials: 397 → 358 ms,
then 399 → 357 ms full exit. All 86 calls, including ten preceding SDK/execution
smoke calls, pass correctness gates. This is local retained-cache evidence, not
cold or Cloud performance. Keep platform/service/TTY checks and PID1 code sharing
as integration requirements, and do not claim the helper explains all wall-time
differences from these overlapping profiles.
