# Application dependency upgrade, 2026-09-10

## Context and experiment

The earlier library test edited a workspace crate's source. This test changes
the application's external bstr requirement and lockfile from 1.12.0 to 1.13.0.
The old version is built first; the first check with the new version retains the
existing source, target and registry caches. It includes downloading the new
crate. The edited lockfile already records dependency resolution, as on both
sides of the ordinary locked check workflow.

The baseline patch was generated by Cargo in an isolated checkout of ripgrep
3fce3b5bb0236da2df6d99672afb8a719642eca7. Only bstr's lockfile entry changes;
the harness checks that every other package entry is identical. Its dependency
changes from serde to serde_core, both already present in the workspace graph.
No application or library source edit is mixed into the upgrade step.

## Reproduction

Build the CLI with the deferred OAuth and transport-readiness changes through
e80290410. The measured binary is /tmp/dagger-rust-cli-readiness; the running
engine embeds upstream 59a9b904d1f237a3effbfe0298c8965a875ef950 and has image ID
sha256:c5f729bfc143414d74c17de37fe73b42d335aceaf2cecbf294587b6d6ef103d7.
From this engine checkout, with the pinned ripgrep reference available:

```sh
DO_NOT_TRACK=1 python3 hack/bench-rust-loop/run.py \
  --dagger /tmp/dagger-rust-cli-readiness \
  --image rust@sha256:39f68a3e8e3ff425f8945ffa91128e60ff930d53e17fbb5214e95824bdd46f1b \
  --ripgrep /tmp/dagger-rust-ripgrep-reference \
  --samples 3 --fresh-engine localhost/dagger-engine.dev \
  --dependency-upgrade --dependency-first native
```

Repeat with `--dependency-first dagger`. Each invocation starts new isolated
caches, warms bstr 1.12.0 and performs one new-version upgrade. Three samples
apply to each preceding ordinary edit scenario, not to repeated A/B dependency
revisits. A third invocation adds `--profile-dependency-upgrade`, with native
first, for the native wcprof recorder.

All three measured trials also exported OTel to a local otlpdump receiver:

```sh
OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:43181
OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=http://127.0.0.1:43181/v1/logs
OTEL_EXPORTER_OTLP_METRICS_ENDPOINT=http://127.0.0.1:43181/v1/metrics
OTEL_EXPORTER_OTLP_TRACES_LIVE=1
```

Pass these as environment variables to reproduce capture conditions. The first
two trials omit the native `--profile` flag, but local OTel export remains on;
they are not telemetry-free baseline measurements. Analytics is explicitly
disabled because automatic approval review rejected the earlier analytics
export probe. Do not claim these wall times represent default analytics-enabled
CLI performance. The exporter choice and opt-out do not change Cargo inputs.

## Correctness and measured times

All three trials checked bstr 1.13.0 and the same downstream package set on both
sides: globset, grep, grep-cli, grep-index, grep-printer, grep-regex,
grep-searcher, ignore and ripgrep. Unrelated memchr remained cached. The package
sets and selected versions are asserted, as are unchanged locked inputs.
Failure, repair and revisiting the earlier invalid source also passed in each
run. This establishes this one upgrade's invalidation behavior, not all Cargo
feature/build-script or concurrency behavior.

| Trial | First side | Cargo via docker exec (ms) | Dagger CLI (ms) | Gap (ms) |
| --- | --- | ---: | ---: | ---: |
| 1 | Native | 1764.25 | 2406.56 | 642.31 |
| 2 | Dagger | 1571.73 | 2181.61 | 609.87 |
| 3, native wcprof enabled on Dagger | Native | 1635.14 | 2213.35 | 578.21 |

Two ordinary samples are insufficient for a tail-latency claim. Do not combine
the third profiled result into their summary. The immediate unchanged followup
took 102.28/455.69 ms (Cargo/Dagger) in trial 1 and 107.92/421.52 ms in trial 2.
Neither the upgrade nor the followup beats Cargo in these measurements.

Complete first-use Dagger checks in the same trials took 48.30s, 26.92s and
28.34s; they are retained in first-use.json, not excluded as outliers. The image
and registry network costs vary substantially. These are empty-engine trials:
Docker, the CLI, engine image, local module source and native Rust image are
preinstalled. Host OS page cache and network caches are not reset. The slim
image is amd64-specific here and lacks git, so both sides skip ripgrep's optional
commit-hash embedding. This is not a host-native or complete-install comparison.

## wcprof attribution

All three extracted OTel traces pass the maintained analyzer's structural gate:
158 operations, one root, 143/143 declared spans received, no missing spans,
open operations, unresolved waits, cycles, orphaned parents or dropped links.
Replay drift rounds to -0.0%. The third native dump has 414 operations, eight
roots, zero open operations and zero dropped events; its window is 1.90s.

The third sample's full process is 2213.35 ms: 51.69 ms before the CLI root,
2154.99 ms inside, and 6.68 ms after. Its combined rsync/Cargo process is
1679.15 ms. OTel's ranking identifies 83.6 ms in trace consumption, 54.0 ms
starting the session, 52.2 ms self time in checks, 39.0 ms in asModule and
38.8 ms in Info RPCs. These are candidate boundaries, not additive estimates of
the gap to native; some spans nest or overlap. The two earlier traces similarly
show multiple 30-45 ms lifecycle/query steps.

Cargo's rounded own duration is 1.52s in the third Dagger run, leaving roughly
160ms within the shell process outside that reported duration. The first two
trials show roughly 170-180ms. Measure source reconciliation directly before
attributing all of this to rsync. The timing does not justify bypassing the
content-based source reconciliation that fixed stale Cargo fingerprints.

Each run retains the exact input diff, package sets, raw Cargo logs, source
copies, CLI/image identity and process boundaries. The harness extractor maps
one measured process to one complete CLI trace for wcprof, including time
outside the root; it does not merge separate CLI invocations. Raw traces and
the private analyzer source are not published. All six trial containers and
all three dedicated engine volumes were verified removed. Ordinary dev-engine
caches and the reference checkout were preserved.

This commit adds a missing workload and stronger measurement evidence. It
contains no new engine optimization and makes no claim that the official Rust
module or the overall performance goal is complete.
