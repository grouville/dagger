Protocol v2 cut response bytes, but this small mechanism trial does not show a consistent response-latency gain. Do not implement another engine admission protocol on this evidence.

The corrected trial completed all 22 anonymous GETs: two explicitly counted primers, seven target-specific first pairs and three reverse-order pairs. Every response was HTTP 200 and validated; all requests after the first reused the same TLS HTTP/1.1 socket. No proxy, credentials, cookies, redirect, retry, reconnection or Cloud export was used. Including the preserved first trial’s two failed-harness primers, total fixture GET attempts were exactly 24. Both trial cohorts and all primers remain separate.

For the ten timed pairs, v0 returned 54,270 body bytes versus 1,910 for v2 (96.5% fewer). Each v2 response was 191 bytes. Maximum measured parsing time was 0.546 ms for v0 and 0.009 ms for v2; maximum body-read time after the first observed application response byte was 0.164 and 0.105 ms, respectively. The dominant interval was still response waiting: approximately 79–181 ms for v0 and 79–199 ms for v2 across these different targets. These ranges describe this sample, not a latency distribution for Dagger.

The order checks matter. For dagger/go, v2 was slower by about 16.0 ms in the first pair and 6.7 ms in reverse order. For go-sdk, the initial 9.7 ms v2 advantage became essentially flat in reverse order (+0.3 ms). TypeScript SDK retained a smaller v2 advantage in both pairs (17.3 and 6.9 ms). Other repositories have only one pair. The complete table is in pairs.md; there is no pooled median or p95 across repositories. The sample cannot distinguish request-order warming, backend variance or a small repository-specific protocol effect.

This was an explicitly scoped host HTTP/1.1 experiment, using one resolved IPv4 endpoint and one verified TLS connection. It did not run the Dagger CLI or engine, compare HTTP/2, demonstrate repository-admission compatibility, or measure cold/edit UX. Initial DNS/TCP/TLS setup is reported separately. The first-byte timer observes a read below the HTTP response parser; it is not packet-arrival time or server CPU time. The earlier approximately 385 ms Git-admission interval union was never assumed fully removable or additive with other work.

The first trial is retained in ../git-advertisement-v2-v1/live-v1-report.md. Its second primer failed an overly narrow harness parser, and its body was not retained. The corrected trial accepted an exact HTTP service banner followed by v2 advertisement, which all eleven new v2 responses used. This does not reconstruct the discarded earlier response. Git’s client accepts the optional service prelude, and its pkt-line rules permit text without a trailing LF; the corrected local tests cover both forms. [Git HTTP client](https://github.com/git/git/blob/v2.55.0/remote-curl.c), [pkt-line rules](https://git-scm.com/docs/gitprotocol-common).

Validation: seven focused groups passed normally and with the race detector before the corrected binary was built. Tests cover wire headers/no credentials, exact request cap, same-socket use, no redirect/replay, status errors, malformed/framing variants, size/header limits, cancellation and first-byte-versus-body timing. The live source/binary/recipe hashes are in manifest.json and live-v2-provenance.json. The observer stores only numeric timings, fixed classifications and public target names; no response body or ref list was saved.

Disposition: keep this as a negative or inconclusive mechanism experiment and stop the protocol change for now. The useful remaining target is work that keeps anonymous admissions or runtime initialization off the actual critical path without weakening per-session visibility checks. This trial does not establish which scheduling change would achieve that.
