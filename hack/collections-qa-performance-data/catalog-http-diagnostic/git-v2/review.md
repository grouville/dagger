A version-2 capability probe is a plausible experiment for a locked HTTP(S) repository, but it is not yet an implemented or proven faster replacement. The measured cost is response waiting, not local reference parsing. No fixture remote was probed during this audit.

Git v2 deliberately separates capabilities from refs: the initial HTTP GET uses the same `info/refs?service=git-upload-pack` resource with `Git-Protocol: version=2`; refs require a subsequent `ls-refs` command. Selective ref prefixes are an optimization and a server may return additional refs. Thus a successful capability response provides no ref, HEAD, tag-peeling or commit-existence evidence. [Official v2 protocol](https://git-scm.com/docs/gitprotocol-v2#_http_transport).

There is positive access-control evidence, rather than a reason to reject v2 outright. Git's HTTP specification requires a forbidden response when repository access is denied and puts authentication at the HTTP layer. The v2 header does not change the repository resource. My inference is that a properly validated anonymous v2 response proves admission to that repository's upload-pack discovery resource on a conforming implementation. It does not prove later access to a particular object; the existing full-ref response is not an object-fetch guarantee either. [Official HTTP authentication and request processing](https://git-scm.com/docs/gitprotocol-http#_authentication).

Native Git provides concrete source support: `http-backend` enters the repository, checks its export permission and selects the enabled service before emitting either v0 or v2 information. Its `get_info_refs` path uses the same checks and then invokes upload-pack. A header-only shortcut that accepts any 200 response would lose this evidence; MIME type and a complete valid protocol response remain necessary. This implementation proof is specific to native Git's HTTP backend, not evidence about the deployment of every Git hosting provider. [Git 2.55.0 http-backend.c](https://github.com/git/git/blob/v2.55.0/http-backend.c).

Capability publication itself is not an authorization implementation: `serve.c` emits advertised commands/features, with repository configuration supplying some values; ref enumeration belongs to `ls-refs`. Host authentication must happen outside or before that stage. The reviewed sources do not establish whether any particular proprietary service exposes generic v2 capabilities before authorization, so that remains a compatibility question, not an observed vulnerability or a fact about GitHub. [Git 2.55.0 serve.c](https://github.com/git/git/blob/v2.55.0/serve.c), [ls-refs.c](https://github.com/git/git/blob/v2.55.0/ls-refs.c).

Dagger can represent the split without inventing a new persistent cache: `publicRemoteProbe` already has separate `public` and nullable `metadata`, and `PrimePublicRemote` ignores nil metadata. Keep the existing per-session probe key, trusted-client credential gate and service-bound exceptions. For a selected, full-commit-pinned HTTP(S) request, a validated v2 response could mark anonymous visibility but leave refs absent; a later actual metadata consumer would perform the ordinary session-owned full lookup. This is an implementation proposal, not authorization proof beyond the protocol/source evidence above.

The request budget is the main tradeoff. Current v0 visibility also supplies all metadata in one GET. A v2-only probe still costs one GET but can avoid enumeration when no refs are needed. If a consumer needs named refs/HEAD, v2 discovery followed by ls-refs or a legacy full lookup costs another exchange. Prefer the existing full advertisement for known unpinned/ref-listing consumers. When a server ignores the v2 header and responds with v0, parse and reuse that response; do not blindly issue a second GET. Empty repositories, hidden refs, malformed packets, HTML login responses, redirects and auth failures need explicit parity tests before changing any default.

The smallest useful local proof is a native git-http-backend fixture with public/private/export-disabled repositories, v2 enabled/disabled, empty/unborn HEAD and annotated tags; count requests and verify public-to-private changes across sessions. Include a deliberately generic capability gateway as a negative-control policy decision: if that response is accepted, document the required HTTP repository-admission contract rather than claiming the packet proves object access. Existing credential isolation and service-bound tests must remain.

Even if these gates pass, no large speedup follows from the current timings. In native http-backend source, response headers are emitted before the child service runs; depending on buffering, remote ref enumeration may occur after first byte. Our observed response wait can include routing, authentication, repository opening, network latency and provider buffering. The post-first-byte interval was only 1–2 ms across all seven responses. A bounded later v0/v2 timing comparison would be needed; do not replace the already-correct permission boundary based solely on smaller payloads.
