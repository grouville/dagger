# Independent review of lazy core metadata

I found no material source-level blocker to upstreaming the narrow production patch with its focused tests. This review reads the patch, the base/view construction and DagQL fork paths, and the test source; it does not claim another test execution.

The production diff changes only ordinary `CoreSchemaBase.Fork`. It forks the already-installed native schema, sets the requested API view, and installs the same core loaders. `dagql.Server.Fork` copies the schema registries and forks object types/install hooks under the existing read lock; it marks interface implementations dirty so reconciliation still happens on first read. Thus skipping the metadata-populated intermediate server does not carry stale interface implementations or lose the legacy view hook.

`buildTypeDefs` reads the installed schema and constructs immutable module-facing values through core metadata functions; it does not install application resolvers into that schema. Actual TypeDefs and core type conversions still enter `CoreMod.viewState`, with the same view mutex, complete metadata construction, name maps and unpruneable cache retention. This removes eager demand for core-only commands and defers identical work for a later module consumer. It is not a new result cache or a wider authority scope.

The patch explicitly preserves the snapshot-share prohibition before ordinary schema construction. The dedicated persisted-decoder fork stays available and unchanged. Tests cover that distinction, legacy/current view visibility, fork-local field isolation, first metadata demand, retained IDs after the first session releases, schema equality before/after metadata construction, and concurrent ordinary forks during first metadata demand. The existing baseline-compatible metadata-content test is useful: it avoids treating opaque wrapper-result identity as the metadata contract.

The module metadata shape projection intentionally omits descriptive fields and some metadata attributes; full callable schema JSON plus existing goldens and the runtime matrix provide complementary coverage. Do not describe that projection alone as an exhaustive metadata comparison. Similarly, the concurrency test validates schema/metadata overlap rather than every possible auth/workspace topology. The implementation does not touch user-default resolution or workspace authority; those risks are not introduced as a new mechanism here.

The direct passive measurement is strong: first-view TypeDef creation accounts for 401–482 ms while base construction takes 9–11 ms and the final ordinary server fork takes 0.2–0.4 ms. Moving the graph into its first real consumer can change wcprof query boundaries and make previously unprofiled work appear inside a query. Report whole CLI results separately, especially for module commands that eventually require the graph. The first diagnostic baseline CLI also had an independent 1.14 s pre-run delay; that is not part of this patch's saving.

Upstream disposition: keep the narrow patch and focused semantic tests; explain the removed dependency (native execution does not require SDK reflection values). Avoid a blanket warm discovery or all-SDK speed claim. The existing frozen ordinary A/B and A/A results, rather than instrumented cold totals, should supply any user-visible timing statement.
