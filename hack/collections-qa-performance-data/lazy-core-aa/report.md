# Same engine binary, different generation exit times

The same-binary control found a **103 ms median CLI difference with essentially unchanged generated-file readiness**, reversing the previous candidate-slot disadvantage. Both retained engine slots ran exactly baseline `bcadd647…`; the lazy-core implementation was absent from both during this control.

After one explicit local and one explicit Cloud generation primer per slot, the three alternating ordinary Cloud pairs were:

| Pair | Original baseline slot | Former lazy slot, running baseline | File ready: original / former | Engine Cloud drain: original / former |
| --- | ---: | ---: | ---: | ---: |
| 0 | 823 ms | 734 ms | 307 / 303 ms | 322 / 306 ms |
| 1 | 837 ms | 724 ms | 301 / 295 ms | 339 / 302 ms |
| 2 | 1,296 ms | 830 ms | 293 / 289 ms | 321 / 340 ms |
| Median | 837 ms | 734 ms | 301 / 295 ms | 322 / 306 ms |

The exit differences are **89, 113 and 466 ms**. Main engine Cloud-drain differences explain only 15, 37 and −19 ms; **74, 76 and 485 ms remain outside the engine shutdown handler**. Generated bytes were already available at nearly the same time. The timer samples file visibility every 5 ms, so these tiny readiness differences are not exact completion-time measurements. Every ordinary command had one recorded GC, with engine cgroup CPU between 0.319 and 0.375 seconds.

Aligning the existing timestamps places nearly all of that residual **after the engine shutdown handler completes**. The handler-completion → CLI-exit intervals are **194.5/195.2/681.0 ms** in the original slot and **125.7/124.2/200.0 ms** in the former lazy slot: differences **68.8/71.0/481.0 ms**. File visibility → estimated handler start lies between −2.4 and +1.2 ms, within the five-millisecond visibility sampling interval. The next useful diagnostic therefore targets CLI cleanup/export after engine shutdown, rather than repeating engine phase counts.

These boundaries use the Docker timestamp of the completion log and subtract the engine's recorded monotonic handler duration. They include small logging/transport scheduling effects and are not exact HTTP send/receive boundaries. They identify a late CLI interval, not the particular provider or network request responsible. The per-pair segments are preserved separately.

This is evidence that the earlier ~80–100 ms warm-generation penalty is not stable to the implementation or slot assignment. It is **not proof of no regression** in either proposed code change, and it does not identify a specific network request or CLI shutdown stage. The existing phase logs cover the engine shutdown handler; the unrecorded remainder includes other engine work, CLI telemetry and cleanup. A command-level diagnostic would be needed to distinguish those costs.

The two local primers measured 1.112 / 1.022 seconds, and the two Cloud primers 1.672 / 1.221 seconds. They are retained separately and excluded from ordinary medians. These are restarted engines on retained independent volumes with unequal earlier cache/history, not cold-volume measurements. Variant order alternated A/B, B/A, A/B for the ordinary pairs; three pairs do not establish a distribution.

All **10 commands passed**: two explicit local generation primers and eight ordinary Cloud commands including two Cloud primers. Every generated file matched the actual unchanged input bytes. Both fixture trees were restored or unchanged. Both owned engines stopped, the original lazy candidate binary was restored while stopped and verified against its prior SHA-256, and no resources were deleted. The original A/B manifests and evidence were left untouched.

This control uses the same normal approved Cloud CLI and native Dang generation UX as the preceding A/B. It adds no profiles, forced GC, relay, timeout changes or background-only completion semantics. Raw stdout/stderr, Docker logs, credentials and trace/session identifiers remain private. The allowlist contains only the frozen public-source driver, sanitized provenance/results, restoration facts and anonymous numeric shutdown phases.
