# Core metadata on demand: real cold and warm UX comparison

The first `dagger ws ls` on a fresh engine volume improved from **1.119 s to 0.745 s** in this matched pair, with normal production Cloud enabled. The engine's Cloud shutdown phase was almost unchanged (151.8 → 156.1 ms); the 374 ms improvement occurred outside that phase. Engine allocation fell from 142.1 MB to 27.7 MB and CPU from 2.095 to 1.107 seconds across the wider command snapshot brackets.

This is deferred work, not deleted work. The first later `-m core api call version` became **0.731 → 1.032 s** and allocated 151.3 → 275.6 MB. Its extra 300 ms also occurred outside shutdown. That is consistent with moving module-facing TypeDef construction to the first metadata consumer. This ordinary series did not collect a first-consumer wcprof, so it does not establish the exact per-operation distribution. First native-generation local primers are recorded separately: 0.648 → 0.504 s, after that core-version call.

The patch changes only `CoreSchemaBase.Fork`: ordinary core schema forks use the installed schema; existing TypeDef consumers retain lazy materialization through the normal view state. It does not add a host result cache, bypass source/authentication checks, or use the separate span-routing experiment. Both engines contain the same frozen metric, withFile, interface and experimental SDK stack. Baseline `bcadd647…`, candidate `56f2eacc…`, unchanged CLI `170e1653…`; complete hashes are in provenance.

Warm generation did not become faster. The generated bytes became visible at median **332 → 326 ms**, whereas CLI exit became slower. The first candidate sample's 704 ms CLI regression is fully within an enlarged engine Cloud drain (263 → 1016 ms; +753 ms), with the output visible 16 ms earlier. However the second pair's 94 ms regression contains only 19 ms of extra Cloud drain; another 75 ms is outside the recorded shutdown handler. The third pair is approximately flat overall. Therefore it is incorrect to attribute the whole warm-generation difference to Cloud, or to claim a causal code regression from these few observations. A separately bounded same-binary A/A control was prepared to probe instance/history/export variation; it had not been executed when this report was generated.

Edited generation likewise needs both boundaries. Candidate output visibility is 362/358/362 ms; baseline is 356/1452/351 ms. The baseline's 1.908 s outlier occurs before output visibility, while its Cloud drain is 35 ms shorter than the matching candidate. The other two candidate samples finish 89–95 ms later, although file visibility differs by only 6–11 ms. Their extra main Cloud drain is only 21–26 ms. There is no wcprof in these ordinary samples to attribute the remaining work.

The baseline selected-check outlier (4.733 s) has 392 ms more Cloud drain, but also 1.912 s more outside shutdown. Its engine cgroup wrote 59.5 MB and the host accumulated 1.113 seconds of I/O `some` pressure across the wider bracket, compared with zero engine writes and 0.094 seconds in the paired candidate bracket. Those counters show concurrent I/O conditions; they do not prove the command spent that time waiting for disk. The second candidate check includes 124 ms of recorded GC pauses yet still completes sooner. Neither aggregate GC nor host pressure should be treated as a direct critical-path explanation.

The three warm artifact pairs all favor the candidate, but Cloud-drain differences explain 200, 370 and 784 ms respectively; the whole CLI differences are 478, 296 and 814 ms. The remaining differences have mixed signs. The local 14-check correctness listing was nearly flat (1.482 → 1.468 s). This experiment establishes neither a general warm artifact speedup from the core-laziness patch nor a general Cloud latency improvement.

Both fresh volumes execute their first real selected check as an explicit local primer: **47.332 → 41.385 s**, with 177.7 → 176.1 seconds of engine cgroup CPU. These first-use compilation/execution costs remain part of the evidence. The trial is not a claim that lazy core schemas remove SDK compilation, test compilation or service builds. The check is `TestFormatResponse`, not all six tests.

All **44 commands passed**: 38 ordinary production-Cloud commands, six explicit local primers/correctness checks. Both full listings contain the expected 14 checks; selected check identity and one-pass output match; every generated file matches the actual input bytes, including three new nonce inputs. No export-error text was detected (this is not server receipt or durable-storage proof). Both original fixture trees were restored/unchanged, both owned engines stopped, no resources deleted. The sampled cumulative engine writes were 4,898,697,216 bytes, below the 8-GiB guard.

Only the first `ws ls` runs on a fresh engine/volume. SDK blobs and the host's image/page caches are available, and engine startup/provisioning is excluded from the CLI timer. First artifact discovery comes after core-version and native-generation calls, so its ~25 seconds must not be labelled fully cold engine latency. One cold pair cannot establish cold-start variability. Ordinary timings contain no extra profiling instrumentation. Every pair and numeric shutdown phase is retained; raw stdout, logs, payloads, IDs and credentials are excluded from this shareable bundle.

The main engine Cloud-drain phase awaits pending exports and a refresh-file gate. Its duration is not a measurement of network RTT, TLS setup, server processing, or an individual HTTP request. File readiness is sampled at 5 ms, CPU/I/O/GC brackets include background work, and the residual outside the shutdown handler includes CLI cleanup. Safe numeric evidence supports these boundaries, not stronger causal claims.
