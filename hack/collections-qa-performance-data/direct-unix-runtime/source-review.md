This experiment compares existing engine transports, without changing CLI or engine behavior. The same original CLI uses container+docker:// for one arm and unix:// for the other; both reach the same engine process. The Unix connector uses net.Dialer and avoids Docker exec setup. Three tunnels can exist with the original separate HTTP pools; changing the transport does not change the pool architecture, session lifetime, authorization headers or joined cleanup.

The private Unix endpoint is exposed through a task-owned host-user directory with mode0700, mounted at /run/dagger in one new owned container. Engine --group uses the host primary GID; the socket must be a socket with mode0660 and that GID before any CLI calls. No engine TCP listener is enabled or published. The existing debug HTTP endpoint is loopback-only for counters/profile capture, outside ordinary timings. Access to the private socket is an engine-access capability; per-client session tokens are retained but are not a replacement for this access boundary.

Both selectors explicitly set the existing Docker image-store override. Otherwise the generic Unix driver has no image loader while the container driver supplies one, making the experiment semantically mismatched. Both connector EngineID methods currently return an empty string. Normal server Info/version handshake remains active, and the core version response is checked against build provenance.

A single retained volume is reused only while its original, precisely identified engine remains stopped. The original container and binary are never modified. The temporary container is checked by immutable ID, owner and mounts, stopped and removed at completion; the retained volume and original container are preserved. A private bind directory is deleted only after its owning temporary container is removed and its ownership/path/socket contents are checked. SDK blob hashes and the diagnostic engine manifest are frozen before starting.

This is a Linux/local-daemon capability test, not an automatic transport implementation. A Docker Desktop or remote daemon does not necessarily expose a kernel Unix socket through the same host filesystem. An upstream fast path should remain behind the normal container connector, preserve provisioning/version checks/image loading, advertise an owned verified endpoint, and retain Docker exec fallback. Docker socket environment syntax alone does not establish this capability. The timing result, not subprocess CPU totals, will determine whether this is worth implementing.

The 56 local CLI calls comprise12 exact primers,36 ordinary warm observations (three alternating pairs for six flows),four native standard-check fail/restore sentinel calls, andtwo full check-list primer/profile pairs. The two profiles are excluded from ordinary summaries. Native generation is fixture generation, not SDK code generation. No cold-volume, service-up, production Cloud or fresh-edit latency claim is supported by this matrix. Existing fixtures remain under the same wide /tmp in both arms.

Raw Unix also bypasses the container driver’s Available→docker version admission probe. These measurements combine that admission difference with replacing Docker exec tunnels; they do not identify the tunnel-only saving. The image loader override preserves attachable behavior but does not restore the skipped driver admission probe.
