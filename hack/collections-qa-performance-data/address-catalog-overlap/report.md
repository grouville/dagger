# Catalog/expansion overlap after opting into baseAddress

The current candidate profile has a 570.5 ms catalog, a 43.1 ms gap to expansion, and 374.4 ms expansion. It does not contain the canonical per-module load markers used by the older readiness experiment. The nine root `ModuleSource.asModule` operations are identifiable by parentage, but their module names are not. Their opaque call digests and nested-client links do not encode the argument names needed to recover Go identity. Assigning names from elapsed time, start order or number of runtime processes would be a guess.

The final anonymous root resolution ends at 552.9 ms after catalog start; only 17.7 ms remains for publication and static catalog work. The earliest root finishes at 220.3 ms. Therefore 350.2 ms is merely the unconstrained maximum window if the relevant collection's entire dependency graph happened to be ready with that earliest root. It is **not** an estimate of the Go pipeline benefit. The prior named diagnostic measured a 167–193 ms Go/backend window on an older remote-source/eager-base stack; that value cannot be transferred to this local-source/Address stack.

The new markers provide a useful negative result: candidate static module-tree construction is 10.38 ms total, and its two core-tree builds total 0.15 ms. Starting those tree builds as individual modules arrive has at most a small static-work opportunity. It cannot explain or remove the 374 ms dynamic expansion. This does not justify a core-type map factory.

A larger pipeline needs an actual Go-ready marker before implementation. The existing prepared module-load readiness instrumentation is suitable: record canonical module name around each resolveModuleLoad task only when profiling, then retain only the known public module names or numeric ordinals in the safe reduction. Put it in the next matched diagnostic engine rather than treating the older profile as current evidence. One fully primed local listing would establish the earliest dependency-complete time and the latest unrelated loader. No new runtime or build is part of this audit.

The Address option removes an important dependency from discovery: Go no longer needs the backend producer to expand module/test keys. However, making every completed module visible immediately is still unsafe. `ensureModulesLoadedModeWithSuccess` holds modulesMu through batch resolution, deterministic error collection, source deduplication and entrypoint arbitration. `serveResolvedModuleLoadsLocked` publishes the chosen module set and required dependencies afterward. `collectArtifacts` then applies entrypoint promotion, SDK generator replacement, include semantics and final global validation/order. A nested workspace demand from arbitrary collection code can re-enter this coordination; a private DagQL server alone does not satisfy sibling module visibility or change the original workspace authority.

Keeping one final output is not enough to preserve semantics. A late promoted-path conflict or required-module error currently prevents enumeration; running an earlier NEVER collection function speculatively may issue external work before that same failure. A safe general pipeline needs a clear dependency/validation contract, deterministic error policy, request-scoped publication and cancellation joins. It must not reuse evaluated receivers across call occurrences, rewrite authority, or introduce a cross-session visibility cache.

A smaller independent boundary is visible in the CLI: `readListedArtifacts` first awaits `selection.ID(ctx)`, then requests `__itemsJSON` from that ID. The 38.7/43.1 ms catalog-to-expansion gaps include remaining first-query processing and the CLI/new-query path; they are an upper bound on this handoff, not all network latency. A supported SDK selector projection could compose the leaf into the original selection while preserving serial catalog-before-enumeration semantics. That is a separate tens-of-milliseconds candidate, not the larger module-load pipeline or a route from 1.1 s directly to 500 ms.

Source-only conclusion: preserve the module option's established saving; measure current named readiness before implementing dynamic overlap. Static factory work is negligible, and blindly removing the batch barrier changes more than scheduling.
