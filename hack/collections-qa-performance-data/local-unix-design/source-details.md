A direct Unix socket is a credible local transport optimization, but the upstream change should stay inside the existing image/container driver. Keep its runtime selection, provisioning, image loader and engine lifecycle; change only how its connector reaches the already selected engine. No implementation or new measurement is included in this review.

The current comparison is a useful ceiling: the same CLI and engine process use either `container+docker://` or the private bind-mounted socket, with the Docker image loader explicitly enabled on both. Raw `unix://` also skips the Docker driver availability probe (`docker version`), so the whole measured difference cannot be attributed solely to `docker exec` or assumed for a connector-only production patch. Sources: `engine/client/drivers/docker.go:25`, `container.go:170`, `dial.go:31`.

The smallest safe design, if the measured saving warrants it, is an optional **managed local endpoint capability** on the container backend. It returns a validated descriptor tied to the exact selected runtime/daemon and full container ID, not just a familiar socket filename or mutable container name. Preserve RunnerHost and the driver so image loading, version selection and cleanup keep their existing meaning. All connections for a client must reach that same engine instance. Reuse the ordinary session headers, attachables, cancellation, terminal telemetry and shutdown flow unchanged.

For newly provisioned eligible engines, create a short, private per-user/per-engine host directory and bind it to a dedicated socket directory. Check directory ownership, mode and symlinks; reject unexpected paths rather than chmod or remove them. Ensure the socket owner/group really maps to the caller on the host. The measured rootful-Linux arrangement (0700 host directory, 0660 socket, explicit host GID) does not establish correct rootless/user-namespace behavior. Socket paths also have a 104-byte limit in the pinned listener helper. Publishing a TCP port or a world-accessible socket is unnecessary.

Locality is the unresolved automatic-provisioning gate. Docker resolves context from flags, environment and config; no DOCKER_HOST variable, or even a Unix Docker endpoint, does not prove a shared host filesystem/kernel. Desktop, a local proxy to a remote daemon, Docker-in-Docker, rootless Docker, Podman/Finch and Apple runtimes need their own capability evidence. A backend lacking proof must use the existing stdio route. Do not infer locality from a host-path string, mount arbitrary host paths against a remote daemon, or attempt `/proc/<container-pid>/root` as a portable user path. A first upstream implementation should support only the validated native-Linux Docker case and leave other backends unchanged; proving that eligibility is part of the implementation, not assumed solved by this benchmark.

Existing containers without a managed socket mount stay on stdio; do not stop/recreate an active engine merely to enable acceleration. Reuse the existing container inspection to obtain the endpoint descriptor where possible, rather than add several Docker CLI probes to every invocation (`container.go:344`). Missing/unavailable sockets may fall back during initial connection establishment, before application bytes are sent. Never retry an arbitrary failed query through another route, and never let a fallback by mutable name switch the client's remaining connections to a different engine. A successful dial to an unverified endpoint is insufficient: the descriptor and handshake need to bind it to the selected container. Negative capability decisions can remain per connector; no cross-session visibility TTL or result cache is needed.

Directory cleanup belongs with managed engine removal, not CLI exit: `--restart=always` and other CLI sessions may still use the engine (`docker.go:62`). On removal, clean only the exact owned endpoint directory after confirming the corresponding container was removed. Do not sweep arbitrary user paths or alter the existing preserved-engine behavior (`container.go:456`). Shared engines created by another local user should fall back to stdio rather than broaden permissions. Exposing a persistent socket also changes revocation behavior for Docker authorization policies: possession of that socket bypasses future Docker-exec checks. This needs an explicit supported authority policy before automatic enablement; per-session tokens do not solve it.

Required tests should build on the current suites:

- Driver fake-backend tests: owned endpoint selected, missing/denied/stale endpoint falls back, custom/remote runtime remains unchanged, no unnecessary warm execs in direct mode, and cancellation while establishing the endpoint. Extend `container_create_test.go` and `container_connect_test.go`; preserve existing failed-tunnel and canceled-waiter tests.
- Identity/permission tests: same container name on two daemon contexts, container replacement, wrong endpoint descriptor, symlink/foreign-owner path, long path, inaccessible socket, and rootless mapping rejection. No fallback may replay application requests or change engines halfway through a client.
- Lifecycle tests: concurrent clients, engine restart, failed startup, exact directory cleanup after engine removal, and older engines without endpoint metadata. Keep `TestImageDriverCreateStartsExistingEngineWithoutListing` and preserved-engine cleanup behavior.
- Real path parity: session secrets, source edits, file synchronization/export, image import/load, a real service, cancellation and final telemetry drain over the direct socket. Reuse `session_attachables_lifetime_test.go`; existing backend integration tests in `container_test.go` are gated by DRIVER_TEST and should only run under a separately scheduled task-owned runtime setup.

This introduces no cache of module answers and changes no SDK invalidation rules. Its scope is connection establishment and owning a privileged local endpoint correctly. The source-only conclusion is feasibility with clear platform/authority work remaining, not readiness to enable automatically everywhere.
