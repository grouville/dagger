Work that the implementation repeats or performs before needing it

1. Schema preparation repeats at distinct boundaries. `NewModTree` builds a module server through `dagqlServerForModule`; persisted tree decoding does so again per module within that decoded tree; `Artifact.Evaluate` deliberately builds a fresh current-session server, memoized only among ancestors of one artifact. Expanded collection evaluation can invoke this more than once in the same command. `dagqlServerForModule` directly calls `buildSchemaWithView`, bypassing SchemaBuilder's existing same-authority prepared-fork reuse. These are source-level possible repetitions; exact execution counts remain to be measured.

   The rebind cannot simply be deleted: cached artifact servers contain field/module provenance owned by a discovering session. Reusing one globally would violate session ownership and defaults. A narrow experiment could supply one request-owned preparation context across evaluation siblings, keyed by attached module-result identity, authority/session/non-module caller, view, and install policy. No lifetime beyond the request, no module-name cache, no caching constructor or collection results. Reuse must create a fork or prove that no subsequent module registration mutates the shared server. The existing SchemaBuilder scope rules in `core/moddeps.go:65` are the minimum authority boundary; cached pointer equality alone is insufficient. Test expired discovering session, two callers with different workspace defaults, different module results of the same name, concurrent values, old/new core views, failure recovery, and snapshot-share decode restrictions.

2. Include narrows module loading, but does not prune static artifact traversal within each module. `collectArtifacts` calls `ModuleArtifactNodes` for the selected module; that collects its whole reachable artifact graph, then `matchWorkspaceInclude` filters at the end (`core/schema/artifacts.go:648–718`). A literal selected path could traverse only compatible prefixes while retaining ancestors needed for constructor defaults and collection dimensions. With M reachable static nodes, d selected depth and b branching along that path, the present work is O(M) per tree; prefix pruning can make a narrow selection proportional to visited compatible nodes. This does not improve unfiltered `list -a`, and no huge constant-factor win is established.

   Preserve both entrypoint shorthand and qualified paths, synthetic naming roots, collection get nodes whose path is transparent, implicit batch replacement, glob/brace escaping and ambiguity checks. For a first patch, optimize only literal prefixes and fall back unchanged for patterns. Do not suppress malformed schema errors that are currently guaranteed before selection without deciding that semantic boundary explicitly.

3. Every configured SDK's engine-managed generator tree is constructed before the same include filter (`core/schema/artifacts.go:663–702`). `sdks()` creates each WorkspaceSDK result, and each `NewArtifactTree` rebuilds an object-type map from all default core type definitions. For an exact Go test path, unrelated SDK provider prefixes cannot match. A conservative name/prefix prefilter can avoid those trees; actual providers matching a wildcard or entrypoint alias must retain the normal path. This avoids local metadata work, not SDK compilation: this code does not run the SDK generator. A generic shared immutable core-name index could separately remove repeated map construction, but the view and retained result ownership must remain explicit.

4. `filterArtifactCommand` computes generator policies for check selections even when none of the selected nodes has a generator ancestor. Policy construction walks parent entries and resolves implementation digests for their modules. The policies are consumed only for a generator ancestor in `enabled`. A pass-local `needsGeneratorPolicy` check could skip it for pure test selections while retaining ordinary module check-skip config. Preserve wrapper suppression and raw-provider skip behavior for staleness checks. This is a clean no-new-cache branch, but likely smaller than module startup and requires attribution before prioritizing.

Entrypoint dispatch is not a free cache boundary

`SchemaBuilder` maintains canonical and sugared servers. Proxies intentionally do not cache; canonical constructor and method selections share the DagQL session cache and perform the real work. Caching a proxy result across commands would skip dynamic constructors/defaults and is wrong. Existing prepared-fork reuse deliberately excludes canonical != self, because proxy closures and canonical loaders must bind together. Rebuilding a sugared schema from a fresh canonical fork may be possible, but the closure binding and both servers' view/cache need explicit tests. It is lower priority than proving repeated standalone artifact schema builds; the selected-check path uses its standalone unsugared module server rather than invoking the CLI proxy namespace.

Proposed next attribution, before any broad patch

Use the default selected-check command with the same exact target and keys. Add numeric per-request counts/durations to module readiness, standalone artifact schema preparation, static tree walk, SDK generator-tree preparation, dimension validation, collection receiver/get/subset, and the selected check resolver entry. Repeat after a fresh semantic source edit, then a no-change invocation, and keep a failed-check/recovery control.

Priority: first establish whether the roughly 1.5 s local selected check is mostly module loading/runtime or repeated schema/selection work. Prefer removing unnecessary preparation over adding a new global cache. Neither source inspection nor aggregate CPU sums support a 500 ms guarantee yet.

One tempting shortcut is not semantics-preserving today. `artifactExpansion.expandNode` enumerates a collection receiver's keys and intersects explicit filters; it does not blindly call `get(requestedKey)`. This preserves the collection's declared membership, returned key order, nonexistent-key no-match behavior, and batching subsets. Replacing enumeration with direct get could execute a key the collection never listed and change errors/order. If selected-key enumeration is the dominant cost, an explicit collection membership/index capability or a module-side efficient key index is the honest route; silently bypassing enumeration is not a safe generic cache optimization. The existing request-local prefix DAG already shares expansion of the same tree/workspace across templates. Any additional sharing should target demonstrated duplicate receiver evaluation or schema preparation, not duplicate that existing DAG.
