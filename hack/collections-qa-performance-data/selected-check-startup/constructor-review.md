Constructor process audit: the generic empty-object fast path already exists

The three Go processes in the retained selected-check profile are different work:

| Role | Process duration | Enclosing call |
| --- | ---: | ---: |
| Register the backend module definition | 86.08 ms | ModuleSource.asModule: 115.04 ms |
| Run authored Backend.New(source) | 78.67 ms | Query.backend: 90.60 ms |
| Run authored Backend.GoTestBase() | 94.70 ms | Backend.goTestBase: 105.93 ms |

These three processes occur sequentially inside Address.container (372.97 ms), before Go collection discovery. Their process durations total 259.45 ms. Enclosing spans overlap their processes and must not be added to them. This is one retained local-only instrumented capture, not a new wall-time comparison or the latest ordinary lazy-core stack. The command reuses its test result: there is no fresh test-runner process in this capture.

The generated backend dispatcher makes the attribution concrete. An empty outer parent name returns dag.Module().WithObject(...), including the constructor metadata. Within the Backend dispatcher, an empty function name invokes New(source), and GoTestBase invokes the corresponding authored method. New stores its contextual Directory in Backend.Source. GoTestBase returns a Go image with the real API service binding and URL. Removing either authored call would change the object state or the check's service configuration.

The engine already has the requested capability boundary. ObjectTypeDef.Constructor is nullable (core/typedef.go:1195). At core/object.go:1229, installConstructor checks whether it is absent. That branch installs a resolver which creates an empty ModuleObject directly at line 1253; it never creates a ModuleFunction or invokes the SDK. The explicit-constructor branch builds NewModFunction, preserves merged defaults, dynamic contextual inputs and implicit cache inputs, then calls fn.Call at line 1310. Thus absence is already an SDK-independent declaration of empty-object construction. There is no second autogenerated-constructor process to eliminate here.

The Go SDK only emits WithConstructor when its parsed authored constructor exists (cmd/codegen/generator/go/templates/module_objects.go:171,272; templates/modules.go:539,558). No authored New therefore already uses the engine path. Static SDK metadata work can remove the first registration process; it does not by itself remove execution of New or GoTestBase. Treat its 86 ms here as a measured component, not a guaranteed end-to-end saving across all modules or cold states.

Do not replace this contract with an inference such as no constructor arguments, no authored __init__, no public fields, or a familiar SDK name. Python materializes a Constructor for its main object (sdk/python/src/dagger/mod/_module.py:154; _resolver.py:303). It may invoke a dataclass constructor, defaults/default factories, an alternate constructor or authored initialization. TypeScript registers an explicit AST constructor when present (object.ts:96 and entrypoint/register.ts:93), and its runtime distinguishes constructor invocation from deserializing state without calling the constructor (registry.ts:256). Dang emits constructor metadata for ConstructorFunction values (core/sdk/dang/v2/helpers.go:676); object bodies/default expressions remain runtime behavior. These SDKs decide what absence means for their object representation; the engine must honor the emitted contract.

The smallest useful next step is therefore not a new empty-constructor flag. For truly empty SDK-generated constructors, the SDK can omit Constructor only after proving its serialized state and initialization semantics equal the existing empty-object contract. That needs SDK-specific conformance tests, but no SDK-specific inference in the engine. Current Go already does this.

For a field-assignment constructor such as this Backend.New, two different options exist:

- Keep normal construction and use the author's existing content-cache policy when the constructor only copies explicit immutable inputs. A previous isolated constructor-only policy experiment removed one warm runtime process, but established no listing wall-time improvement. Its fresh-edit constructors correctly still ran. This is not a generic edit-to-500-ms solution, and caching GoTestBase across sessions would require preserving its mutable image and service semantics.
- A future explicitly declared field-initializer capability could describe a typed argument-to-field mapping plus typed literal defaults. It must be opt-in, schema/versioned, validated against canonical fields/types, and preserve dynamic defaultPath/ignore resolution, null/missing distinction, result ownership and normal call identity. Any SDK default factory, custom initializer, ambient API read, validation/error or side effect must keep the normal runtime constructor. Inferring this capability from arbitrary user code would expand the scope substantially; no such patch or speed claim is proposed now.

If such a declarative capability is pursued later, the engine should reuse the existing explicit constructor FieldSpec and DynamicInputsForCall rather than bypass input admission. It could replace only the body invocation with typed object-state construction. Existing module_constructor_test.go covers basic argument/field transfer, fields-only constructors, errors and Python/TypeScript default factories. module_runtime_behavior_test.go:297 covers empty fields with and without a constructor. module_path_inputs_test.go:1952 covers source changes through defaultPath. Additional capability tests would need omitted vs explicit null/default inputs, nested object/list fields, current-client Directory ownership, edits/overlays, error fallback and metadata-only construction that actually launches zero SDK processes. None of these tests was run in this source-only audit.

Disposition: do not implement a duplicate empty-constructor fast path. Continue static registration work already in flight and the separate source-safe contextual-base investigation; retain exact user-defined constructor semantics. The measured schema-fork work is only milliseconds and is not the priority suggested by this profile.
