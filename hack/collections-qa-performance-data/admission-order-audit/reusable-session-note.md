An explicit reusable Dagger session is a plausible larger experiment; simply keeping a client open does not establish a correct edit loop.

There is already an appropriate user-facing starting point: `dagger api with-session <command>` keeps a connected owner alive and injects a loopback port/token (`internal/cmd/dagger/run.go:30,158`). `dagger api session` is hidden SDK plumbing, while `dagger shell` opens a project container/directory terminal, not a host command-session switch. A long-lived SDK Client likewise retains its connection. `engine/client.Params.SessionID` and the engine’s registered nested-client transports provide internal building blocks for a deliberately owned session and distinct client lifetimes; registration requires a held parent scope and immutable ancestry (`engine/server/client_scope.go:21`).

A useful prototype would keep owner S alive, allocate a fresh non-module child C for each normal command, bind C to its own explicitly declared workspace and fresh host/env attachables, and join/close C at command completion. It would share S’s existing session-scoped anonymous admission and immutable content cache. This must not share C’s mutable workspace detection, pending modules, loaded schemas or env snapshot. Existing nested clients can inherit their parent workspace (`engine/server/session_workspaces.go:119,206`), and the Go SDK’s FromSessionEnv path explicitly rejects changing the workspace/workdir (`sdk/go/engineconn/engineconn.go:63`). Therefore wrapping an edit loop in with-session or inventing a new client ID is not proof of freshness.

The admission behavior would change intentionally: a repository becoming private during this explicit session keeps the existing cached public result until S ends, just as current within-session logic documents (`core/schema/git.go:1258`). Credentialed metadata remains separately keyed by auth identity (`core/git_remote.go:190`), but the main client’s credential providers and refresh lifetime must also be reviewed. Fresh child IDs alone do not invalidate every PerSessionInput function; session policy must specify which effects remain session-cached versus command-fresh. This is explicit session lifetime, not an invisible TTL extension.

There may also be a fixed-cost benefit: only the main client’s shutdown performs the foreground Cloud session drain and stops session services (`engine/server/session.go:2755`); every child still flushes workspace locks and local session telemetry. Moving the owner’s close outside individual commands changes the Cloud completion boundary and service lifetime, so measure final owner teardown separately and retain errors. No milliseconds are predicted from these source facts.

The decisive gate is a before/after sequence with real external file edits, comment-only changes, test rename/add/remove, module config/SDK/lock updates, selected workspace/env changes and credential rotation. Verify no stale reads from inherited owner state; workspace read epochs currently advance after engine exports, not arbitrary editor writes. Include a PerSessionInput witness, anonymous-public-to-private transition, private token A/B isolation, service-bound repositories, child cancellation/sibling isolation, parent termination, error recovery, complete output parity and bounded memory after many child commands. Report per-command full exit and final-session drain separately. Without these tests, a fast repeated query on one SDK Client only measures a different cache lifetime.
