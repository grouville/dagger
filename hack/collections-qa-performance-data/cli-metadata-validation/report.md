The JSON metadata proof needed the same request module-demand classification as the existing metadata query. Without it, an unscoped workspace API call asked for metadata before pending workspace SDKs and modules had been loaded. The CLI therefore saw no `go` command. Explicit `-m` module calls had already loaded their module and did not expose this omission.

The fix recognizes `__currentTypeDefsJSON` at both existing request-demand boundaries. It retains the old scoped module selection, entrypoint fallback, union with other demanded root fields, and one-shot scope consumption. It does not unconditionally load every workspace module. GraphQL aliases are resolved to their actual field name before this classification.

Validation used an unchanged-source fail-first overlay. The old `currentTypeDefs` cases passed, while the new JSON root failed full-schema classification and aliased scoped-demand consumption. The corrected candidate passed the exact new tests and the three existing demand-selection tests normally (9.94 s including test build) and under the race detector (16.56 s). These are correctness-test durations, not CLI performance results.

The only difference from the preceding closure candidate is this request-demand correction. Both measured CLI binaries are unchanged. No engine runtime or Cloud call was performed by this validation/build step. Live collection and schema-edit correctness remains the next gate; the prior failed runtime is retained separately.
