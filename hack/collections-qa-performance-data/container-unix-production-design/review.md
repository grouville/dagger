The first automatic implementation can avoid an additional Docker inspection by targeting the managed image driver. Its existing warm path already runs ContainerExists, implemented as `docker container inspect --format {{ .ID }}`, followed by ContainerStart. The inspect result is currently discarded except for its success status. Extend that existing lookup to return a selected-container descriptor rather than adding a second inspection. This is different from the explicit `container://` benchmark path, which has no such lookup today.

For newly provisioned eligible engines, create a short private per-user endpoint directory and an unpredictable generation identifier before ContainerRun. Mount the directory, configure socket ownership, and label the managed endpoint. Capture the full container ID already printed by `docker run -d` instead of discarding it. Atomically record the endpoint descriptor with that immutable ID and the effective backend/daemon context. On later image-driver invocations, the existing inspection can return the current immutable ID, managed label and actual mount together. Validate those against the owned local descriptor and socket permissions. Replaced containers or changed contexts must invalidate selection, rather than trusting a reused name or a familiar path.

This removes a redundant probe, not the need for identity evidence. The effective daemon context must come from the backend's actual selection rules, including environment/config precedence; a Unix DOCKER_HOST or an absent variable is insufficient. The existing backend abstraction does not currently expose that descriptor, so this remains implementation work. Do not introduce a successful-endpoint TTL keyed only by name. For arbitrary pre-existing `container://` engines lacking managed provenance, retain stdio initially rather than bolt a new inspection onto every command or guess ownership.

An engine-side endpoint generation value could also be verified in the existing BuildKit Info exchange, before session attachables start, without another network roundtrip. Today that exchange validates only the Dagger package and version; Revision is the engine name/hostname. Connector.EngineID currently returns empty and is propagated as telemetry metadata, not used to authenticate this binding. A dedicated optional capability field/header would require actual client/server validation; merely populating EngineID or comparing version strings would not implement it. All later connections and any establishment-only fallback must remain bound to the same selected immutable container. Never retry an application request through a different route.

The socket is a persistent engine-access capability. Its directory follows engine lifetime and concurrent clients, not CLI lifetime. New managed engines can expose it; old active engines should retain stdio without recreation. Native rootful Linux is the demonstrated platform. Remote contexts, Desktop, rootless mappings, other runtimes and authorization-plugin policies need explicit capability/authority decisions, not silent inference. In particular, persistent socket access bypasses future Docker-exec authorization decisions; default enablement cannot pretend existing session secrets solve that boundary.

The smallest next implementation should therefore extend existing managed provisioning/lookup, keep backend selection and image loading, and establish a verified local endpoint with safe fallback for unsupported/old engines. It should not start with a global socket cache or a new daemon. Tests need to cover two daemon contexts with equal container names, name replacement, endpoint-generation mismatch, older engines, permissions/symlinks, restart and concurrent-client cleanup, and rejection before attachables when identity verification fails. The opt-in50-call proof measures the useful transport mechanism, not this missing automatic lifecycle.
