The cleanup-overlap correction passes its lifecycle tests but does not repair the shared-transport performance regression. Keep both shared-transport variants isolated; neither is recommended for production adoption from these measurements.

Three CLIs were freshly built from the same HEAD0d source, parent metadata implementation, dependency bytes and flags. Original uses separate API/telemetry pools; serial shares one per-client transport but joins physical cleanup after other cleanup; concurrent schedules that same fully joined owner in the existing cleanup group. The owner still joins established connections and pending dials. Nothing is allowed to escape after CLI exit.

The experiment contains 12 counted exact-flow primers, 36 ordinary warm commands and six sentinel fail/restore calls: 54 local commands total, all correct. All four flows run in three rotated triples ABC, BCA, CAB. Every time includes CLI spawn through full process exit. Engine startup/stop and out-of-process counters are excluded. There are no Cloud calls or profiler-enabled commands.

The strengthened deterministic test gates actual client net.Conn.Close start and completion separately from another cleanup task. It proves both resources are joined, and that physical closure can proceed while the other task is blocked. Both release orders fail on serial-v1 and pass on the correction. The full focused normal and race suites also pass, including real HTTP/2 final telemetry, cancellation, reconnect, partial initialization and pending-dial cleanup.

The first new witness used a real HTTP/2 server inside synctest. It passed on the correction, but a later test crashed when x/net/http2 reused a pooled channel outside that synctest bubble. That failed fixture run is preserved. Only the witness was replaced with a directly owned gated net.Conn and a fake shutdown response; real HTTP/2 lifecycle coverage was retained and rerun. The production overlap patch did not change during this fixture correction.

This narrow trial validates core API version, workspace listing, native API output, already-current native generation, and intentional native check failure/restoration. It does not validate a new expanded 14-row listing result or measure actual SDK generators, fresh edits, cold starts or Cloud overhead. The earlier broader 90-command trial covers its own distinct flows.

Both fixture bytes and the original engine binary were restored; the engine was stopped and no resource was deleted. The next useful investigation would attribute specific API/drain/physical-close phases with separate local diagnostics. More ordinary repetitions without a causal measurement are not justified by this result.

Generation paired CPU does not isolate physical-close waiting. Concurrent minus original CLI-plus-children CPU is +16.4 / +6.5 / +39.0 ms, while engine CPU brackets are +54.3 / −8.2 / −122.7 ms. Concurrent minus serial CLI-plus-children CPU is also higher in all three (+21.4 / +11.9 / +29.6 ms), although wall time improves in the last triple. Thus the evidence supports neither a pure added-wait explanation nor consistently more engine work. Both shared variants fully join the same owner; the original has weaker physical cleanup ownership, which also limits comparisons of process-tree accounting. These are aggregate counters, not timed Close stages.
