Independent source review found no new adoption blocker in the corrected shared HTTP/2 owner. This review ran no tests or commands against an engine; it verified source hashes against the recorded normal/race results and the matched runtime build inputs. Runtime performance and correctness results remain separate evidence.

API and telemetry retain distinct request cancellation domains. API Do links the request context to closeCtx and keeps that link through the response body; error or Body.Close releases it. Closing an API stream sends cancellation to that stream rather than closing the shared physical connection. Telemetry still derives from the client-owned internal lifetime, so command cancellation cannot discard final records. Normal Close retains shutdown response, bounded terminal-frame drain, internal cancellation, cleanup and final telemetry join before closing the shared transport. No final exporter is moved to a detached goroutine.

Failed Connect now cancels API requests and internal telemetry, joins initialized telemetry consumers and closes the owned transport, including active streams. Both Connect entrypoints initialize the cancellation functions before installing this cleanup. Cleanup still preserves the original initialization error. Existing attachables and BuildKit defers remain intact. The tests exercise both ordinary/e2e attachables cleanup and a partially opened telemetry subscription.

The transport registration mutex prevents WaitGroup.Add racing with Close.Wait. After closed is set, no new dial can register; already-started dials either publish before the snapshot or close their late connection before decrementing pending. Concurrent transport Close calls wait for the same closeDone. The corrected gated-dial test proves both callers wait for late connection cleanup, and its earlier-owner negative witness fails as intended. This is a join guarantee, not a universal hard timeout: a connector that never returns, or a physical Close that never returns, can still delay cleanup. The existing container driver deliberately detaches command-process lifetime from the opening request, and the Docker command connection has its own process termination behavior. Do not describe the total Close path as strictly bounded solely because the telemetry drain has a timeout.

Authority remains per Client, not global. Both wrappers keep their own immutable header sets and use the existing SecretToken injection. The shared pool cannot cross Client/session objects, and each HTTP request still carries authorization and client metadata. Connection setup preserves opening-context values while detaching cancellation only after handoff; request cancellation still interrupts establishment. No credential lookup, remote authorization policy, GraphQL cache identity or Cloud publishing decision changes.

The standard HTTP/2 transport remains responsible for stream capacity and any protocol-defined retry behavior. The max-three-stream test fills all telemetry streams and proves an API request can open a second physical connection instead of deadlocking. The change does not introduce a custom retry loop around GraphQL/API requests or replay a failed user operation. Existing telemetry cursor reconnect and permanent-error rules remain unchanged and covered. A shared physical connection necessarily correlates transport failure across streams; that is different from one stream returning an HTTP error. The suite covers stream failure and telemetry reconnect, but does not explicitly inject a mid-body physical connection loss during a side-effecting API request. That would be useful additional regression coverage; the source contains no new API replay policy to fix.

The warm tunnel count changes from three extra tunnels to two because the normal topology is one initial control connection, one attachables connection and one shared API/telemetry connection. The driver still dials on demand if peer stream limits or additional clients require more. The negative topology witness fails against the original constant and the candidate passes. This is not a hard cap of three physical connections.

The supplied normal/race suite covers separate headers, API body cancellation, client cancellation, final telemetry records, repeated/concurrent Close, failed shutdown, partial initialization, slow stream flow control, pending establishment, reconnect and old telemetry forwarding behavior. It supports the lifecycle change substantially beyond a dial-count-only assertion. The local90-command matrix can establish current fixture behavior, but production Cloud, remote-engine latency and every transport/backend are not implied by this source review.
