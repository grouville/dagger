The isolated split-init prototype has no remaining source-review blocker for its focused test and matched runtime gates. This is permission to measure the design, not a production or performance endorsement. Reviewed file hashes are in `independent-review-inputs.json`.

The boundary preserves the behavior that matters: the light PID1 keeps the original `mainInit` body, signal forwarding, process-group behavior, reaping and exit status. The heavy session helper remains a separate process with its own session. Moving attachables into PID1 goroutines would instead expose their `exec.Cmd.Wait` calls to PID1’s global `Wait4(-1)` reaper; this prototype avoids that ownership change. The heavy binary recognizes both the old `/proc/self/exe` and new fixed `/.dagger-session` entrypoints.

The helper keeps the existing inherited environment, session identity and FD3 readiness protocol. FD3 EOF deliberately means ready or helper death, as before. The engine adds two read-only mounts for initialized execs, including ordinary execs, while `NoInit` adds neither. Keeping the helper mount for all initialized execs also preserves explicit `DAGGER_SESSION_TOKEN` environment usage, rather than guessing that only nested-client metadata can require it. The new fixed in-container path and extra mount are observable packaging costs and must be included in the real comparison.

The test cleanup issues raised in review were addressed before execution: readiness cleanup cancels the helper and waits for its startup goroutine before inspecting its process; signal failure cleanup joins the owned child; argv execution has a 15-second context; the opt-in real PID-namespace case has a 30-second context and a joining `CombinedOutput`. Killing that owned namespace PID1 also ends its descendants. The namespace test remains explicitly opt-in. The recorded test source covers ordinary/nested/NoInit mount behavior, FD3 readiness and early death, argv/exit status, signals and namespace reaping. No passing result is asserted by this review.

A fair engine comparison must package the same freshly compiled heavy binary, including both aliases, in both arms. Only the PID1 selection and required light/helper mounts should differ. SDK agent confirms that this is the planned composition. Include ordinary exec, nested SDK/check execution, errors, cancellation/service teardown and image packaging in the later gate; an isolated process-start microbenchmark cannot establish whole-command gains.

Before upstreaming, share the lightweight PID1 implementation instead of maintaining a second approximately 200-line copy. Existing pipe-close/error behavior is copied rather than newly fixed; broad cleanup changes should not be mixed into this causal performance test.

The saved 58/67 ms pre-dispatch intervals include runtime/container startup, PID1, the heavy helper, SDK/user initialization and nested admission. They do not measure Go package initialization alone and are not a predicted saving. The next runtime comparison must determine whether removing heavy imports from PID1 changes the user-visible critical path.
