# Metadata allocation candidates: upstream scope and remaining work

Status: the parent is running a fresh matched nine-flow engine comparison. This note records the already completed source review, library tests and microbenchmarks; it makes **no whole-CLI latency claim**. Frozen build inputs and manifests are unchanged. The fresh control includes the existing experimental SDK stack, so its absolute latency is not a production-main baseline.

## Independent production patch: visible interface signatures

`interface-signatures/prototype.patch` changes only `dagql/interfaces.go`, `dagql/server.go` and focused tests. It is suitable for an independent Dagger commit/review once the matched runtime checks are accepted. It does not depend on Dang, the TypeScript fixture, new public APIs, persistent caches or a dependency bump.

Reconciliation previously rebuilt an interface's visible field slice for each candidate pair and fixed-point sweep. It now lazily obtains that slice once per interface needed in the current locked reconciliation/view. Empty signatures are memoized correctly; if every relationship is permanent, no memo map is allocated. A new pass gets new signatures. Existing field ordering, last matching declaration/version, permanent facts, covariance, contravariance and greatest-fixed-point elimination stay unchanged.

Let P be the number of pair checks across all sweeps, I the number of interfaces actually consulted, and F the signature size. **Signature materialization** changes from O(P·F) to O(I·F), with O(I·F) temporary retained signature space. Pair enumeration, argument lookup and the fixed-point algorithm are unchanged; this does not make overall reconciliation linear.

Focused existing/new tests pass, including view/version precedence, empty and duplicate declarations, later-pass edits, recursive conformance and rejection, permanent relationships, argument/list/null variance and introspection. The final race run passed (1.245 s package time). Three alternating compiled microbenchmark cycles measured dirty 100-object/8-interface/4-field reconciliation at **2.033 → 1.289 ms**, with **2,033,578 → 514,211 B/op**. At 1,000 objects it was 18.740 → 12.111 ms. An all-permanent pass retained exactly 623 allocations and 73,408 B/op in both variants; its approximately 1% timing difference is noise. These are local algorithm measurements, not a command-level forecast.

The motivating eight-command allocation capture attributed 87.5 MiB of sampled `FieldSpecs` allocation to compatibility checks. That cumulative allocation is neither per command nor an exact predicted saving. Evidence: `../interface-signatures/{results.md,prototype.patch,source-manifest.json,race-lazy.log,lazy-benchmark-runs.json}`.

## Experimental dependency patch: Dang scalar/nil clone leaves

`dang-clone-leaves/prototype.patch` belongs to the isolated Dang syntax-cache prototype, not current production Dagger. It is a separable improvement to that experiment, but it should **not** be presented as an independently upstreamable production cache enablement. Production adoption needs a maintained Dang API/dependency revision and a reviewed syntax/state ownership contract; generated typed cloning is preferable to an open-ended reflection clone.

The candidate avoids allocating a temporary reflected destination for scalar and nil leaves. The enclosing clone still copies the value into its owned destination. Non-nil pointer graphs, slices, maps and mutable source positions retain their existing deep cloning, alias tracking, visit budget and rejection rules. Complexity remains O(AST nodes); this reduces constant allocation/work, not the number of AST traversals.

Unit tests passed (0.117 s), including the existing concurrent inference/content-invalidation cache tests. Race tests passed (2.054 s). Additional tests cover mutable isolation, aliases/cycles, source filename/ranges, typed nil versus empty values, unsupported/private state and clone-budget charging. Three alternating microbenchmark cycles measured a real Go-module source cache hit at **5.047 → 4.342 ms**, **1,769,971 → 1,612,440 B/op**, and **38,839 → 23,041 allocations/op**. Alternating filenames and a large mutable AST also passed and improved. Bytes fell only about 8–9%; a 40% allocation-count decrease must not be described as a 40% memory or whole-command reduction.

Evidence: `../dang-clone-leaves/{microbench-results.md,manifest.json,prototype.patch}`. The fresh build variants enable production DagQL reuse first, then add the clone leaf change, allowing independent attribution.

## Read-only follow-up: fewer Dang clones before inference

These are concrete source opportunities, not implemented or benchmarked changes:

1. **Registration reads the same syntax twice.** Frozen `helpers.go:moduleDeclaredTypeNames` calls `ParseFileCached` only to inspect public top-level object/interface/enum/scalar names. It discards that owned tree. `DeclareDir`/`RunDir` then calls `parseDirBlocks`, which obtains a second owned tree before declaration/full inference. Ordinary calls with `IncludeSelfInDeps` already skip the first pass. The existing profile has 12 `dang.selfTypes` operations, but does not count files/clones per operation; no saving can yet be multiplied from those span durations.
2. **A cold syntax-cache miss makes an unused validation clone.** The singleflight loader calls `cloneSyntax` before publishing a pristine template; `ParseFileCached` then calls it again to return an owned tree. A loader-local clone could be returned only to that loader invocation, while followers still clone the shared pristine template. Never return the validation clone through the shared singleflight result. Preserve unsupported-AST fallback, each caller's filename and concurrent isolation.
3. **A narrow library-owned declaration summary can avoid the first deep clone.** Store only parser-derived public top-level names beside the immutable content-keyed template, expose copied strings, and continue applying module namespace/schema authority in Dagger per invocation. Keep ordinary diagnostics, the main-type seed on parse failure, nested/private exclusions and source-size fallback. A stronger alternative is a pass-owned parsed-directory handle: inspect its names, then transfer its owned blocks once to declaration inference. That requires care with project-import loading and diagnostic timing, which the existing best-effort name pass intentionally defers.

Do not cache an inferred tree or environment by filename, module ID or source bytes. `declareDirectoryFiles` mutates forms to insert imports; AST nodes embed `InferredTypeHolder`; full inference and evaluation attach scope/client state. `DeclareDir` deliberately skips body inference while `RunDir` performs it. An immutable syntax tree plus separately allocated per-invocation inference state could eventually remove most cloning, but that is a wider Dang architecture change, not a safe local memoization. The next diagnostic should count cache hit/miss, validated/returned clones, files and visited nodes separately for name-only, declaration and runtime paths without recording source/path payloads.

## Read-only follow-up: relation-removal worklist

The current compatibility predicate is a conjunction of fixed signature facts and named `ImplementsChecker` facts. Exact-name matches are constants; return covariance requests (object type, interface type), and argument contravariance requests the reversed pair. Lists/nullability and extra required arguments are fixed structural conditions. There is no negation of candidate relations in these checks.

This makes a worklist plausible: seed the same candidate/permanent relations, evaluate each non-permanent signature once using the full initial relation set, record every required candidate relation for successful checks, seed removals for failures, then propagate removal along reverse dependency edges. A pure dependency cycle with no impossible member survives, preserving the greatest fixed point. Permanent relations remain facts even when structurally incompatible. Relations absent from the initial universe remain false. Retain current sorted publication and the final interface-cycle guard; changing publication order could alter which direct relationships are recorded.

For V candidate pairs, signature-check cost C, and E recorded dependencies, the elimination phase could become O(V·C + V + E) work and O(V + E) extra state. The current whole-set rescanning can require O(V) sweeps in a long rejection chain, with O(V²·C) worst-case signature checking (plus repeated sorted enumeration). This does not eliminate the O(objects·interfaces + interfaces²) candidate universe, and E may be large. One-sweep/permanent-heavy schemas may lose to adjacency construction.

Before implementing, count unresolved pairs, sweeps, checks, relation dependencies and removals on the real profile workload, and compare dependency chains with recursive cycles and permanent-heavy cases. Existing profiles establish repeated signature allocation, not that multi-sweep propagation dominates latency. A cheaper sorted-name snapshot may be worthwhile if repeated `RangeSorted` work is material, but its allocation/CPU contribution has not been attributed here. Keep this algorithm change separate from the small reviewed signature-reuse patch.
