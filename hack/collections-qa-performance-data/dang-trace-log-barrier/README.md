This is an isolated, uncompiled source prototype. No test, engine invocation or performance comparison has run for it. It changes Dang v2 completion only; Dang v1, full FlushTelemetry, ClientTelemetry, periodic metrics and shutdown remain on their existing paths.

The latest saved profile has 15 `dang.flushTelemetry` intervals: 51.881 ms inclusive sum, 48.970 ms union. Those are whole barriers, not measured metric time. The saved profile has no trace/log/metric subphases or per-client collection markers. Existing flush debug fields count retained identity records, whereas actual metric work uses live client runtimes. Neither field nor the number of module calls proves how many metric readers were collected. No 49 ms saving is claimed.

Each successful authored Dang v2 invocation currently flushes the shared session trace provider, the shared session log provider, then snapshots and concurrently ForceFlushes every live client's MeterProvider. Each provider has one actual PeriodicReader locally and a second when session Cloud publishing is configured. Each reader collects observables and exports; it is not just empty queue bookkeeping. Client metricMu serializes concurrent flush/reclamation of that client's readers. For F completion barriers and A_i active runtimes at barrier i, metric work scales with the sum of A_i, with up to two reader collections per provider call. Quiescent runtimes are removed after their final collection, so this is not the earlier assertion of quadratic growth in every historical client.

The concrete proposal is an explicit `FlushSessionTraceLogs` API. It resolves the caller through the same client-record lookup and flushes the ENTIRE shared session's trace/log pipeline. It does not select a client subtree, cache a visibility result, skip payload processing, change origin routing, start background work, or weaken an existing full-flush API. A single private implementation handles full and trace/log-only barriers; both retain trace-then-log ordering and errors.Join behavior. Dang v2 keeps its same wcprof parent phase and debug-only handling of a flush error.

Metrics remain owned by five-second periodic readers, synchronous quiescent-runtime shutdown, and final session shutdown. Full FlushSessionTelemetry and ClientTelemetry still collect all live clients' metrics. This DOES change incidental metric sampling: a sibling's transient observable gauge value present only at an unrelated Dang completion may no longer be sampled at that point. It is a deliberately narrower new barrier contract, not byte-for-byte metric equivalence. Final collection does not reconstruct arbitrary earlier gauge samples. This contract needs maintainer acceptance before adoption.

Current clients of ClientTelemetry are log capture, descendant/span inspection, and trace-report inspection; their present queries read spans/logs rather than metrics. They remain unchanged in this prototype, including the wider full barrier. The final safety gate is that required logs, live/end span updates, payload visibility and cleanup observations remain correct; no assumption that all telemetry is optional is being made.

Relevant prior art must remain visible. [PR #13841](https://github.com/dagger/dagger/pull/13841) narrowed the old per-client providers to the calling client and descendants; [PR #13852](https://github.com/dagger/dagger/pull/13852) reverted it after suspected workspace path-safety and partial service-startup flakes. The public discussion does not establish the root cause. We must not present that as a proven specific routing bug or reapply its subtree selection. The new design keeps the current all-session shared trace/log queues and their origin routing intact. Later commits 23e33cb6b3, c41a6fcba9, 83f7de93df and 9d6dc7815b changed provider ownership, separated identity from live runtime, reclaimed quiescent runtime state and restored per-runtime metric ownership. Those differences make this a new design to test, not a reason to ignore the revert.

Cloud behavior is unchanged. The session's bounded Cloud trace/log processors make ordinary provider ForceFlush a no-op; main-client shutdown separately drains them within its existing budget. Thus the measured Dang barrier is not a per-call Cloud HTTP drain. The metric Cloud reader can still enqueue collections at full barriers, periodic ticks and final shutdown. No queue/exporter ownership or retry policy is changed.

A separate pre-existing nuance is retained: Dang flush runs before JSON marshaling and before evalDangSource's deferred SpanStdio.Close emits stdout/stderr EOF. That means the current barrier itself never promised those final EOF records were already visible. The prototype keeps this ordering. The focused tests exercise a subsequent explicit barrier delivering the EOF records, but an eventual actual Dang/captureLogs integration gate must ensure the complete existing lifecycle remains sound. The scoped transport closes and drains after eval; metrics reclamation can still occur there.

The profiling-only overlay adds fixed names around trace/log/aggregate-metric phases and each actual per-client MeterProvider.ForceFlush, with no IDs, arguments or payloads. Per-client phase start is AFTER metricMu acquisition, so its count equals actual provider calls; aggregate metric time includes scheduling and mutex waits and should not be reconstructed by summing child durations. A nil/already-reclaimed provider emits no child marker. This allows a baseline profile to tell whether metric fanout is material before attributing a performance improvement. Existing BeginOp disabled behavior is used, with no new generic counter system.

Prepared focused gates use real session providers/SQLite routing and real PeriodicReaders:

- One caller's completion makes both its and an unrelated sibling's live spans/logs visible under unchanged origin routing, collects zero metrics, accepts later end/EOF updates, and leaves full flush plus final shutdown delivering values 41 then 42 through both readers.
- A real log BatchProcessor with a blocked exporter cannot return from the barrier before its record is exported.
- Actual SDK providers preserve trace-before-log invocation, join both errors, and propagate cancellation from either phase.
- A blocked unrelated metric shutdown does not block the new barrier; the existing full barrier still waits and final values still export exactly once.
- Missing client/session context is rejected through the existing lookup.

A negative overlay routes the new barrier back through full collection, so the zero-metric test must fail. Existing reclamation, session routing, metric-final-collection and Cloud single-delivery suites remain required regressions. Normal/race compilation is NOT yet run. The prototype does not establish actual Dang runtime/captureLogs integration correctness by these unit gates alone.

Source layout: `profile-overlay.json` instruments the unchanged full baseline; `source-overlay.json` contains the production candidate; `test-overlay.json` adds mock API compatibility and the focused tests. `negative-overlay.json` is the expected-failure variant. The source hashes are frozen in manifest.json. No shared worktree file is changed.
